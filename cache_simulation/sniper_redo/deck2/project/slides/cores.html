More cores, a bigger prefetching gain

How to read it

One line per read count. Height is the time saved by the L1 and L2 prefetchers together, against a run with no prefetcher. Higher is faster.

What we found

One core: 4% to 12% saved. Four cores: 13% to 16%. At 8 and 16 cores on 50 reads: 18%. On the 16 GB database at 16 cores: 24.9%.

Caution

With few reads per core, start-up work is a large share of the run, and part of the multi-core gain may be that. Not tested.

All values are Sniper simulated time, with and without the prefetchers, at the same core count, read count and database. The baseline has no prefetcher at all, so the gain on the real machine, whose CPU already has prefetchers, would be smaller. Instruction count at 50 reads rises from 52 M on one core to 87 M on 8 cores and 130 M on 16 cores, which is thread start-up and splitting overhead. A control (a 4-way LLC change) stayed within 0.9% of base at every core count, so the gap is not noise. The 8 and 16 core runs at 10 and 25 reads were still running when this was built; the graph marks the missing points.
