Caution

At 100 reads the multi-core gain rises to 22% to 25%, so start-up work alone does not explain it. More cores also do not speed kraken2 up here, so something serial limits it. Cause untested.

All values are Sniper simulated time: the time the simulated CPU would take to run the job, taken from Sniper's elapsed_time counter for the slowest core. Printed cycles are the same quantity times 2.1 GHz. It is not Sniper's own run time on Luna. The baseline has no prefetcher at all, so the gain on the real machine, whose CPU already has prefetchers, would be smaller. Table values are rounded to 0.1 ms; the saved percentages are computed from the unrounded times. File sizes: 10, 25, 50 and 100 reads are 7.9 K, 37 K, 91 K and 164 K bases. 16 GB database at 16 cores, 50 reads: 24.9% saved. Why the multi-core gain rises at 100 reads is not known. With more reads, start-up work becomes a smaller share, so a start-up explanation would predict a smaller gain, not a larger one. In these runs the no-prefetcher time barely changes with core count at 100 reads (17.9 ms on one core, 19.6 on 4, 18.2 on 8, 17.5 on 16), so something serial dominates. One possibility, not tested here, is the serial section that reads the input file in order, which is a streaming pattern prefetchers speed up; an earlier real-machine result in this project also found serial reading of the FASTQ to be a limit on scaling. A control (a 4-way LLC change) stayed within 0.9% of base at every core count, so the gain is not noise.
