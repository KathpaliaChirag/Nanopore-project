Caution

Same gain at 10, 25 and 50 reads on 8 and 16 cores, though 10 reads on 16 cores is mostly thread start-up. So much of it is likely start-up work. Not proven.

All values are Sniper simulated time: the time the simulated CPU would take to run the job, taken from Sniper's elapsed_time counter for the slowest core. Printed cycles are the same quantity times 2.1 GHz (8 cores, 50 reads, no prefetcher: 18.65 M cycles from the time, 18.6 M printed). It is not Sniper's own run time on Luna, which was minutes to hours. The baseline has no prefetcher at all, so the gain on the real machine, whose CPU already has prefetchers, would be smaller. Table values are rounded to 0.1 ms; the saved percentages are computed from the unrounded times. 16 GB at 16 cores, 50 reads: 24.9% saved. Instruction counts: 10 reads takes 7.3 M instructions on one core but 32 M on 8 cores and 64 M on 16 cores; 50 reads takes 52 M, 87 M and 130 M. The extra instructions are thread start-up and splitting overhead, and they grow with the core count. That is consistent with the gain growing with cores while staying flat across read counts, but we have not tested it directly. A control (a 4-way LLC change) stayed within 0.9% of base at every core count, so the gain is not noise.
