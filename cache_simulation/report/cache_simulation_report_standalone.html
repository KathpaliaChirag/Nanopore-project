What a software cache does for kraken2, cycle by cycle

Kraken2 classifies DNA reads by looking up short fingerprints (minimizers) in a huge hash table. That lookup is slow because it waits on memory. We asked whether a small software cache in front of the table speeds it up, and how the answer changes with the cache's shape, its size, the CPU's own caches, the database and the workload. Every number below comes from a detailed Sniper simulation and is read straight from the committed data files.

Nothing here is measured on real hardware

Everything is simulated, on one thread. The last real-hardware benchmark (Aug 30, three databases, six thread counts) found no speedup from the cache at all. So the wins above are simulated wins at small workloads. Whether they survive production-size runs is still open.

What "no cache" really means

Stock kraken2 already has a one-entry memory: it remembers the last minimizer and its answer, and skips the table search when the next window repeats it. S0 keeps that. Our S2 build keeps it too and puts a real table (many entries, several slots per group) in front of the hash-table search. So "S0" is "no S2 table", not "zero caching". Details in what is inside S2.

How to read the numbers

Simulator terms

TermMeaning
SniperA CPU simulator. It runs the real compiled kraken2 and models the core, the caches and the memory cycle by cycle. Its settings change the simulated machine, not kraken2 itself.
Detailed modeFull timing model: cycles, IPC, cache hit rates. Every result on this page is detailed mode. It runs roughly 25 to 200 times slower than fast-forward.
Fast-forward modeRuns the program without timing. Fast, and its printed IPC is meaningless. Used only for setup checks (the smoke test and the first tracing).
CyclesThe simulated CPU clock ticks a run took. This is the real-time proxy: cycles ÷ clock speed = simulated time.
Wall-clock / elapsedHow long Sniper itself took on the host. It tracks instruction count, drifts between sessions and is not program speed. Early results used it by mistake; see the corrections.
IPCInstructions per cycle. Higher means fewer stalls per instruction. Checked on every row: cycles ÷ instructions must equal the reported IPC.
Ways / sets / lineA cache is split into sets; each set has several ways (slots) that one address may occupy; a line is 64 bytes moved at a time. More ways means fewer collisions but more slots to check.
Unique cache linesHow many distinct 64-byte lines the run touched. A footprint measure.
NUCANon-uniform cache architecture: the shared L3 is modeled as one slice per core on a mesh, not one block. Luna's L3 (105 MB) becomes 96 slices of 1,125 KB.

What is real and what is a placeholder

Real: cache sizes, ways and line size for Luna and (partly) the laptop. Placeholder or borrowed: the L3 speed (tag 15 / data 20 cycles), the L3 replacement policy (LRU, though the real chip differs), memory timing (a generic DDR4-2400 model), and the CPU core model (inherited from a different chip; Sniper has no Sapphire Rapids core). Every machine here uses the same stand-in x86 core, so machine comparisons test cache configuration, not real ARM or AMD behavior.

Four bugs found getting the config to load

  1. Wrong -c syntax. A path (config/luna.cfg) silently fell back to defaults. The correct form is the bare name, -c luna.
  2. Comma-joined flags. -c base,luna triggers Sniper's heterogeneous per-core mode instead of chaining files. Two separate -c flags are needed, base first.
  3. Cache-size validation abort. Sniper requires size = sets × ways × line exactly. A 1,120 KB target had to be rounded to 1,125 KB (1,200 sets).
  4. Crash with a non-power-of-2 set count. The default xor_mod hash goes out of range when sets is not a power of 2. Switching the L3 to plain mod fixed it. The same check later caught the flat-L3 config (114,688 sets is not a power of 2).

There was also a false start: kraken2 is a Perl wrapper script, so pointing Sniper at it instrumented Perl's start-up and showed near-zero work. Finding the real compiled classify binary (with strace) and its raw arguments fixed it.

Software cache · Luna hardware · steps 9 to 11

Width sweep: 4 to 64 ways at 10 reads

First real comparative experiment · 50 MB database · 10 reads

Does a wider software cache cost more or help?

WIDER IS WORSE
What we did
Ran six kraken2 builds through Sniper on the same 10-read workload, changing only how many slots (ways) each set of the software cache has: 4, 8, 16, 32 and 64, plus one row called "baseline".
Why
An earlier sweep on real hardware found more ways was slower, but its cache kept global atomic hit/miss counters that made threads fight. The "noatomics" builds delete those counters, so any slowdown left belongs to the width itself.
Result
Instructions, cycles and cache lines touched all rise with width. 64-way needs 11% more cycles than 4-way and touches 4.3× more cache lines. IPC stays flat (1.76 to 1.80), so the extra cost is more instructions, not more stalls.
What we learned
The real-hardware trend (more ways is worse) reproduces with the thread-locking overhead removed, so it is not an artifact of that overhead. It is consistent with wider caches simply having more slots to touch and check.
Caveat: the "baseline" row is not stock kraken2

That build already contained an early version of our S2 cache (its numbers are almost identical to 4-way, so it is probably a 4-way). The true stock build (S0) was identified in the next step. So this sweep compares S2 widths against each other only. It is also a tiny 10-read workload, where start-up work dominates.

Software cache · Luna hardware · steps 12 to 20

Database size: the cache's value flips with the database

Five variants × four databases · 50 reads · 20 runs in one batch

Does the S2 cache help, and at which width, as the database grows?

WINS ON 8 GB+LOSES ON 50 MB
What we did
Ran stock kraken2 (S0) and four S2 widths (1, 4, 8, 16-way) on four databases: 50 MB, 8 GB, 16 GB and 103 GB, all on the same 50-read workload with Luna's cache setup. A 1-way (direct-mapped) build did not exist, so it was built from scratch and its output checked identical to S0.
Why
A small database's table mostly stays warm, so a lookup is cheap and a cache has little to save. A huge database's table is scattered, mostly cold memory, so a lookup is expensive and a cache that intercepts repeats should pay off. We wanted to see where the split falls.
Result
On 50 MB every width is slower than stock (0.85 to 0.91×). On 8, 16 and 103 GB every width is faster (1.8 to 2.05×), and 4-way is best or tied everywhere. On 8 GB the stock run needs 68.1 M instructions at IPC 1.32; 4-way needs 51.9 M at IPC 1.84.
What we learned
The value of a software cache depends on the database, not on the cache. 4-way is the sweet spot: 16-way adds cost and touches far more memory for no gain. The benefit rises to 16 GB then dips slightly at 103 GB (1.97× vs 2.05×), so it may be approaching a ceiling.
Three corrections made on the way to this table

1. Wall-clock contamination. The 1-way and 8-way runs overlapped other jobs, so 1-way looked 122% slower than 4-way at the same cycles. Their wall-clock was discarded and re-run. 2. Cross-batch drift. Batches run hours apart ran at 14 vs 8 seconds per million cycles, so wall-clock cannot be compared across batches. One "final fair batch" ran everything together. 3. Wrong metric. Sniper's wall-clock measures the simulator, not the program. By that measure 1-way "wins"; by cycles (the right measure) 4-way wins. Use the metric selector below to see both.

Software cache on different hardware · steps 20 to 21

Does the win depend on the machine's caches?

Luna · desktop · Orin-sized · your laptop · 4-way vs stock

Same software cache, four simulated machines

NOT MONOTONIC IN CACHE SIZE
What we did
Rebuilt the simulated machine with other cache setups (config-only overlays: cache sizes, ways, clock) and reran stock and 4-way on the same 50-read workload. Luna and the desktop and Orin configs ran 50 MB and 8 GB; your laptop config came from the laptop sweep (8 GB only).
Why
To check the 50 MB result is not an accident of Luna's cache geometry, and to see whether smaller CPU caches make a software cache more or less valuable.
Result
50 MB is a small loss on every machine (0.90 to 0.92×). On 8 GB the win is 1.83× (Luna), 1.94× (desktop), 1.65× (Orin-sized), 1.94× (laptop).
What we learned
Consistent in direction everywhere, so the pattern is not a Luna quirk. But the size of the win does not follow cache size: the desktop (smaller L2) gains more than Luna, and Orin (smallest caches) gains least. Orin's stock run is already cheaper (55.9 M vs the desktop's 60.6 M cycles), possibly because of its larger L1, but that is a guess.
Caveat

These are config-only stand-ins on the same x86 core model, not real ARM or AMD behavior, and Orin's L3 associativity is a placeholder. Each machine changes several things at once (sizes, ways, clock), so no single knob can be blamed.

Software cache · Luna hardware · steps 22 to 24

2,000 reads: does the small-database loss fade with more data?

50 MB database · 2,000 reads (35.1 M bases) · five variants · 12 to 15 hours each

Was the 50 MB loss just a warm-up effect of a tiny workload?

LOSS HOLDS AND GROWS
What we did
Ran the same 50 MB database at 2,000 reads, 40 times the earlier 50-read run, for stock and all four widths.
Why
At 50 reads the cache lost by about 10% on this database. The obvious excuse was that 50 reads is too little for a cache to warm up.
Result
Every width loses to stock, and by more than before: 4-way 1.28× slower, 1-way 1.31×, 8-way 1.34×, 16-way 1.39×. Cost rises steadily past 4-way.
What we learned
Not a warm-up problem. Two mechanisms show: 1-way suffers conflict misses (too few slots), while 8 and 16-way pay for checking more slots per lookup even though their hit rate rises. 4-way sits between the two costs.
Correction to our own explanation

This job was first described as showing "the earlier ~2× speedup was a small-workload artifact". That was wrong: this job uses the 50 MB database, which was already losing at 50 reads. The ~2× win lives on the 8 GB+ databases, which this job never tested at scale. The finding is only that the small-database loss holds at 40× the data.

Software cache · your laptop's cache setup · step 26

Laptop sweep: read count × database × width

Ryzen 7 5800H config · 8 GB and 16 GB · 10, 50, 100, 500 reads · stock and 1, 4, 8-way · 32 runs

Does the large-database win hold as the workload grows?

WINS SMALLLOSES LARGE
What we did
Ran every combination of four workload sizes, two big databases and four builds (stock, 1, 4 and 8-way), 32 runs, on the laptop's simulated cache setup. The biggest run took about 9 hours.
Why
The fair batch only used 50 reads. The open question was whether the 8 GB+ win survives larger workloads, the same test we had already run for the small database.
Result
At 10 reads the cache is 3.3 to 3.6× faster; at 50 reads about 2×. At 100 reads 8 GB flips to a loss (1.03 to 1.06× slower) while 16 GB still wins (up to 1.08× faster). At 500 reads both lose: 8 GB 1.09× slower, 16 GB 1.02× slower. 4-way is the best width in every row.
What we learned
The win shrinks steadily with workload size and reverses. Bigger databases hold the win longer (16 GB flips later than 8 GB), but two databases are too few to call that a rule. Width ranking never changes; only the sign does.
Confound: the "reads" axis is not clean

The 10 and 50-read files are short reads (786 and 1,827 bases on average, 8 K and 91 K bases in total). The 100 and 500-read files come from the front of a long-read file (47 K and 51 K bases per read, 4.7 M and 25.4 M in total). Between 50 and 100 reads the count doubled, but the sequence grew about 50-fold, exactly where 8 GB flips. See the long-read test that separates these.

Software cache · laptop setup · 8 GB · step 45

Long-read scaling: what drives the flip?

10, 25, 50 long reads from the same file as the 100 and 500-read runs · stock vs 4-way

Read count, read length, or total bases?

CROSSOVER AT 2 TO 5 M BASES
What we did
Cut the first 10, 25 and 50 reads of reads_fast_2000.fastq (0.35 M, 0.90 M and 1.87 M bases, 35 to 37 kbp per read) and ran stock and 4-way on the 8 GB database. Together with the sweep's 100 and 500-read rows from the same file, that gives a five-point curve where read length stays roughly constant.
Why
To separate read count, read length and total bases, which all changed together in the laptop sweep.
Result
4-way beats stock by 42% at 10 long reads (1.42×), 20% at 25, 4.5% at 50, then loses by 3% at 100 and 9% at 500.
What we learned
Read length alone does not cause the loss: 10 reads of about 35 kbp each still win by 42%. The advantage falls steadily with total sequence and flips between 1.87 M and 4.7 M bases.
A suspicious constant in the small-workload wins

The second chart shows stock minus 4-way instructions. It is +14.4 M at 10 long reads and +14.2 M at 25, the same number even though the data grew 2.6×. A per-read saving from the cache would grow with the data. This looks like a fixed difference in start-up code between the two builds (they come from different kraken2 source snapshots, and Sniper simulates the whole program including start-up). Part of the small-workload win may therefore be a start-up artifact, not the cache. The test that settles it is to run both builds on about 1 read.

Software cache · size axis · steps 27 to 34

Cache size: 2,048 to 1,048,576 sets

Six size-pinned 4-way binaries · four databases · run by two sessions in parallel

Is there a cache size that helps?

SIZE DOES NOT MATTERONE ANOMALY AT 65,536
What we did
Found that kraken2 fixes the cache size at compile time (a formula sets it from the L3 size and the thread count, clamped to 4,096 to 262,144 sets). Built six binaries with the size pinned to 2,048, 4,096, 16,384, 65,536, 262,144 and 1,048,576 sets, all 4-way, and swept them over four databases. Each build's classification output was checked identical to stock.
Why
Every earlier test changed the number of ways at whatever size the formula picked. Nobody had varied capacity itself. A tuned size might be where the real gain hides.
Result
Flat within 0.7% of each database's median at five of six sizes, on every database. The one exception is 65,536 sets: +6.3% (50 MB), +2.5% (8 GB), +1.0% (16 GB), +6.0% (103 GB), then back to baseline at 262,144 and above. On 50 MB, stock kraken2 (14.1 M cycles) beats or ties every size.
What we learned
Capacity is not the lever, on small or large databases. The best-supported explanation for the 65,536 spike is a hash-distribution artifact of this workload file's minimizers at that one mask width, not a general size law. It is unproven.
Data caveats for this sweep

Mixed workloads. The 50 MB and 103 GB ladders used 10 reads; the 8 GB and 16 GB ladders used 50 reads. Do not compare their cycle counts to each other. Different cache. These binaries are the current S2 design (heap-allocated, 16-byte entries, hash-mixed set index), not the fixed-4,096-set builds used in the width tests. Not in the verdict chart. The 16 GB ladder was left out of fig14 and shows the weakest spike.

Verdict of the size research brief · step 33

Five agents, three iterations, four hypotheses

A two-session research pipeline. Five independent agents each analysed the existing data, wrote a plan, then debated to a written conclusion, three times, folding real new runs in between. Iteration 2's leading mechanism (a linear start-up cost proportional to cache size) was overturned when the 103 GB data showed the spike reverting at larger sizes.

#HypothesisVerdictKey evidence
H1The small-database loss is structural, not a sizing problemCONFIRMEDStock 14.1 M cycles ≤ all six sizes on 50 MB; hardware associativity null triangulates on the same near-zero reuse
H2The large-database win grows with cache capacityREFUTEDFive of six sizes on 8 and 103 GB are cycle-identical; the one different size is a loss
H3The best size is a fixed fraction of the databaseREFUTED (location)Anomaly at the identical 65,536 sets across a 2,000× database range; its size varies (+1.0 to +6.3%), so magnitude is database-dependent
H4Kraken2's default sizing formula is near-optimalCONFIRMED, TRIVIALLY, AT ONE THREADNothing beats it because nothing beats anything at one thread. Says nothing about the multi-thread regime the formula governs; a real-hardware null exists there too. Recommendation: do not retune the formula
Practical recommendation from the brief

Stop tuning cache size. Redirect effort to eviction policy under real thread contention and to Thesis 2 (cell width and double hashing), which none of this touched.

Hardware only · no software cache · steps 25 and 35

Hardware L3 associativity: 1 to 30-way

Stock kraken2 · Luna setup · 36 runs across three databases

Does the CPU's own L3 associativity change kraken2's speed?

NO EFFECT
What we did
Kept stock kraken2 (no S2 table) and changed only the hardware L3's associativity: 1, 4, 8, 15 (Luna's real value), 16 and 30-way, at fixed slice size (1,125 KB, so the set count changes with the ways). First on 50 MB at 10, 50, 100 and 500 reads (24 runs); then on 8 GB and 16 GB at 50 reads (12 runs).
Why
Every other experiment varied the software cache. This is its mirror: does the hardware's own associativity matter, independent of any software cache? It had never been isolated.
Result
Cycles do not move: under 1% spread at every workload size on 50 MB (at 500 reads: 4,523 to 4,538 M), 51.7 to 51.8 M on 8 GB, exactly 60.7 M on 16 GB. There is no trend with associativity.
What we learned
Almost nothing on this workload is resolved at L2 or L3: those hit rates stay under about 2%. Lookups are nearly all an L1 hit or a full memory miss, so tuning the mid-level caches has nothing to act on. It also explains why the software cache fails on small databases. The bottleneck is memory latency, not cache organisation.

Hardware only · step 36

Flat L3 versus the per-core mesh model

Stock kraken2 · Luna setup · 50 MB and 8 GB · 50 reads · 4 runs

Does modeling the L3 as one bank instead of 96 slices change the answer?

TOPOLOGY MATTERS
What we did
Rebuilt Luna's L3 as a single 105 MB, 15-way bank (114,688 sets) instead of 96 per-core mesh slices, keeping the same latencies, and ran stock kraken2 both ways.
Why
Every Luna experiment assumed the mesh-slice model. The simpler flat model might have given the same numbers, which would make the extra modeling unnecessary.
Result
The flat model is slower on both databases: about 31% more cycles on 50 MB and 17% more on 8 GB. IPC falls from 1.47 to 1.12 and from 1.32 to 1.13.
What we learned
The mesh model is not just extra realism: it changes the result. The flat bank's very different set count (114,688 vs 1,200 per slice) changes tag lookup and conflict behaviour. Caveat: every run uses one simulated core, so this shows the latency-model effect and would be larger for a multi-core workload.
Data caveat

In flatl3_comparison_2026-09-15.csv the l3_hit_pct column reads 0 for both mesh rows. That is a bug in the run script (it never fell back to the mesh statistic). Cycles, instructions and IPC are unaffected.

What is inside the S2 cache

Each kraken2 lookup goes through up to three stages. The S2 table is only the middle one.

StageWhat happensWhere the data lives
1. One-entry memorySame minimizer as the previous window? Reuse the stored answer. Stock kraken2 has this; our builds make it per-thread so it survives across reads.Two variables, 16 bytes: register or L1
2. S2 table (ours)Different minimizer: look in a set-associative table of recent answers. On a miss, do stage 3 and insert the result.Ordinary RAM, private to each thread; the CPU pulls hot parts into L1, L2, L3
3. Hash tableThe real search of the database's hash table.The database: 50 MB to 103 GB of mostly cold memory
A correctness rule built into the code

The S2 table only decides whether stage 3 must run again. Hit counting and species counts stay tied to "different from the immediately preceding minimizer", exactly as stock kraken2 does. Otherwise the cache would silently change the classification report. Every build's output was checked identical to stock.

Correction logged 2026-09-19

An earlier log entry said the fair-batch 4-way binary "is already the 262,144-set point". Measuring each binary's per-thread memory showed it is 4,096 sets. So the width tests and the size test use different implementations of S2.

The sizing formula

Current S2 sets the number of sets to floor(0.25 × 105 MiB ÷ (ways × 16 B × threads)), rounded down to a power of 2 and clamped to 4,096 to 262,144. At one thread and 4 ways that gives 262,144 sets (16 MiB). Two real bugs were fixed on the way: a crash at large sizes with 16+ threads, and a slowdown cliff at 1,048,576+ sets from touching every entry at start-up. Neither ever triggers at the sizes the formula picks, and the full real-hardware benchmark (three databases, six thread counts, three runs) found stock, early S2 and final S2 statistically indistinguishable. Our size sweep found no size that beats the others at one thread.

The set-index fix

The original index used the minimizer's raw low bits. Measured on the 8 GB database, one set absorbed 225× the average load while another was never touched. Mixing the bits with MurmurHash3 first raised the hit rate from 0.40% to 3.58% at the same capacity, but changed no wall-clock time on real hardware.

What "noatomics" means

The first S2 kept global hit and miss counters updated with atomic operations from every thread. With 32 to 96 real threads they fought over one memory location and caused a 2 to 3× artifact on the 50 MB database. The noatomics builds remove only those counters. What the cache stores is unchanged. Our Sniper runs use one thread, so it mostly keeps instruction counts clean.

Is S2 the only difference from stock?

Not strictly

The source audit found that stock (S0) and our S2 tree are different snapshots of kraken2. The S2 tree's base has program structure S0 lacks (for example a daemon mode), classify.cc differs by about 490 lines even before any S2 code, and the S2 tree also carries the project's other patches: per-thread one-entry memory, the S2 table, the sizing formula and heap allocation, the set-index hash fix, and a prefetch-batching patch. The minimizer lookup loop itself is identical, the hash-table code differs by about 3 lines, and classification output is byte-identical, so most of any difference is very likely the S2 table. But it has not been proven. A clean test builds S0's own source with only the S2 table added.
