What a software cache does for kraken2, cycle by cycle

Kraken2 classifies DNA reads by looking up short fingerprints (minimizers) in a huge hash table. That lookup is slow because it waits on memory. We asked whether a small software cache in front of the table speeds it up, and how the answer changes with the cache's shape, its size, the CPU's own caches, the database and the workload. Every number below comes from a detailed Sniper simulation and is read straight from the committed data files.

Nothing here is measured on real hardware

Everything is simulated, on one thread. The last real-hardware benchmark (Aug 30, three databases, six thread counts) found no speedup from the cache at all. So the wins above are simulated wins at small workloads. Whether they survive production-size runs is still open.

What "no cache" really means

Stock kraken2 already has a one-entry memory: it remembers the last minimizer and its answer, and skips the table search when the next window repeats it. S0 keeps that. Our S2 build keeps it too and puts a real table (many entries, several slots per group) in front of the hash-table search. So "S0" is "no S2 table", not "zero caching". Details in what is inside S2.

How to read the numbers

Simulator terms

TermMeaning
SniperA CPU simulator. It runs the real compiled kraken2 and models the core, the caches and the memory cycle by cycle. Its settings change the simulated machine, not kraken2 itself.
Detailed modeFull timing model: cycles, IPC, cache hit rates. Every result on this page is detailed mode. It runs roughly 25 to 200 times slower than fast-forward.
Fast-forward modeRuns the program without timing. Fast, and its printed IPC is meaningless. Used only for setup checks (the smoke test and the first tracing).
CyclesThe simulated CPU clock ticks a run took. This is the real-time proxy: cycles ÷ clock speed = simulated time.
Wall-clock / elapsedHow long Sniper itself took on the host. It tracks instruction count, drifts between sessions and is not program speed. Early results used it by mistake; see the corrections.
IPCInstructions per cycle. Higher means fewer stalls per instruction. Checked on every row: cycles ÷ instructions must equal the reported IPC.
Ways / sets / lineA cache is split into sets; each set has several ways (slots) that one address may occupy; a line is 64 bytes moved at a time. More ways means fewer collisions but more slots to check.
Unique cache linesHow many distinct 64-byte lines the run touched. A footprint measure.
NUCANon-uniform cache architecture: the shared L3 is modeled as one slice per core on a mesh, not one block. Luna's L3 (105 MB) becomes 96 slices of 1,125 KB.

What is real and what is a placeholder

Real: cache sizes, ways and line size for Luna and (partly) the laptop. Placeholder or borrowed: the L3 speed (tag 15 / data 20 cycles), the L3 replacement policy (LRU, though the real chip differs), memory timing (a generic DDR4-2400 model), and the CPU core model (inherited from a different chip; Sniper has no Sapphire Rapids core). Every machine here uses the same stand-in x86 core, so machine comparisons test cache configuration, not real ARM or AMD behavior.

Four bugs found getting the config to load

  1. Wrong -c syntax. A path (config/luna.cfg) silently fell back to defaults. The correct form is the bare name, -c luna.
  2. Comma-joined flags. -c base,luna triggers Sniper's heterogeneous per-core mode instead of chaining files. Two separate -c flags are needed, base first.
  3. Cache-size validation abort. Sniper requires size = sets × ways × line exactly. A 1,120 KB target had to be rounded to 1,125 KB (1,200 sets).
  4. Crash with a non-power-of-2 set count. The default xor_mod hash goes out of range when sets is not a power of 2. Switching the L3 to plain mod fixed it. The same check later caught the flat-L3 config (114,688 sets is not a power of 2).

There was also a false start: kraken2 is a Perl wrapper script, so pointing Sniper at it instrumented Perl's start-up and showed near-zero work. Finding the real compiled classify binary (with strace) and its raw arguments fixed it.
