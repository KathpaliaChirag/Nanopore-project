Hardware only · no software cache · steps 25 and 35

Hardware L3 associativity: 1 to 30-way

Stock kraken2 · Luna setup · 36 runs across three databases

Does the CPU's own L3 associativity change kraken2's speed?

NO EFFECT
What we did
Kept stock kraken2 (no S2 table) and changed only the hardware L3's associativity: 1, 4, 8, 15 (Luna's real value), 16 and 30-way, at fixed slice size (1,125 KB, so the set count changes with the ways). First on 50 MB at 10, 50, 100 and 500 reads (24 runs); then on 8 GB and 16 GB at 50 reads (12 runs).
Why
Every other experiment varied the software cache. This is its mirror: does the hardware's own associativity matter, independent of any software cache? It had never been isolated.
Result
Cycles do not move: under 1% spread at every workload size on 50 MB (at 500 reads: 4,523 to 4,538 M), 51.7 to 51.8 M on 8 GB, exactly 60.7 M on 16 GB. There is no trend with associativity.
What we learned
Almost nothing on this workload is resolved at L2 or L3: those hit rates stay under about 2%. Lookups are nearly all an L1 hit or a full memory miss, so tuning the mid-level caches has nothing to act on. It also explains why the software cache fails on small databases. The bottleneck is memory latency, not cache organisation.

The default view plots each run's cycles as a percent difference from the same workload at Luna's real 15-way, so all workload sizes share one axis. Sources: hw_assoc_sweep_2026-09-14.csv (50 MB), hw_assoc_sweep_bigdb_2026-09-15.csv (8 and 16 GB). Charts: fig12, fig13.

Hardware only · step 36

Flat L3 versus the per-core mesh model

Stock kraken2 · Luna setup · 50 MB and 8 GB · 50 reads · 4 runs

Does modeling the L3 as one bank instead of 96 slices change the answer?

TOPOLOGY MATTERS
What we did
Rebuilt Luna's L3 as a single 105 MB, 15-way bank (114,688 sets) instead of 96 per-core mesh slices, keeping the same latencies, and ran stock kraken2 both ways.
Why
Every Luna experiment assumed the mesh-slice model. The simpler flat model might have given the same numbers, which would make the extra modeling unnecessary.
Result
The flat model is slower on both databases: about 31% more cycles on 50 MB and 17% more on 8 GB. IPC falls from 1.47 to 1.12 and from 1.32 to 1.13.
What we learned
The mesh model is not just extra realism: it changes the result. The flat bank's very different set count (114,688 vs 1,200 per slice) changes tag lookup and conflict behaviour. Caveat: every run uses one simulated core, so this shows the latency-model effect and would be larger for a multi-core workload.
Data caveat

In flatl3_comparison_2026-09-15.csv the l3_hit_pct column reads 0 for both mesh rows. That is a bug in the run script (it never fell back to the mesh statistic). Cycles, instructions and IPC are unaffected.
