What is inside the S2 cache

Each kraken2 lookup goes through up to three stages. The S2 table is only the middle one.

StageWhat happensWhere the data lives
1. One-entry memorySame minimizer as the previous window? Reuse the stored answer. Stock kraken2 has this; our builds make it per-thread so it survives across reads.Two variables, 16 bytes: register or L1
2. S2 table (ours)Different minimizer: look in a set-associative table of recent answers. On a miss, do stage 3 and insert the result.Ordinary RAM, private to each thread; the CPU pulls hot parts into L1, L2, L3
3. Hash tableThe real search of the database's hash table.The database: 50 MB to 103 GB of mostly cold memory
A correctness rule built into the code

The S2 table only decides whether stage 3 must run again. Hit counting and species counts stay tied to "different from the immediately preceding minimizer", exactly as stock kraken2 does. Otherwise the cache would silently change the classification report. Every build's output was checked identical to stock.

Correction logged 2026-09-19

An earlier log entry said the fair-batch 4-way binary "is already the 262,144-set point". Measuring each binary's per-thread memory showed it is 4,096 sets. So the width tests and the size test use different implementations of S2.

The sizing formula

Current S2 sets the number of sets to floor(0.25 × 105 MiB ÷ (ways × 16 B × threads)), rounded down to a power of 2 and clamped to 4,096 to 262,144. At one thread and 4 ways that gives 262,144 sets (16 MiB). Two real bugs were fixed on the way: a crash at large sizes with 16+ threads, and a slowdown cliff at 1,048,576+ sets from touching every entry at start-up. Neither ever triggers at the sizes the formula picks, and the full real-hardware benchmark (three databases, six thread counts, three runs) found stock, early S2 and final S2 statistically indistinguishable. Our size sweep found no size that beats the others at one thread.

The set-index fix

The original index used the minimizer's raw low bits. Measured on the 8 GB database, one set absorbed 225× the average load while another was never touched. Mixing the bits with MurmurHash3 first raised the hit rate from 0.40% to 3.58% at the same capacity, but changed no wall-clock time on real hardware.

What "noatomics" means

The first S2 kept global hit and miss counters updated with atomic operations from every thread. With 32 to 96 real threads they fought over one memory location and caused a 2 to 3× artifact on the 50 MB database. The noatomics builds remove only those counters. What the cache stores is unchanged. Our Sniper runs use one thread, so it mostly keeps instruction counts clean.

Is S2 the only difference from stock?

Not strictly

The source audit found that stock (S0) and our S2 tree are different snapshots of kraken2. The S2 tree's base has program structure S0 lacks (for example a daemon mode), classify.cc differs by about 490 lines even before any S2 code, and the S2 tree also carries the project's other patches: per-thread one-entry memory, the S2 table, the sizing formula and heap allocation, the set-index hash fix, and a prefetch-batching patch. The minimizer lookup loop itself is identical, the hash-table code differs by about 3 lines, and classification output is byte-identical, so most of any difference is very likely the S2 table. But it has not been proven. A clean test builds S0's own source with only the S2 table added.
