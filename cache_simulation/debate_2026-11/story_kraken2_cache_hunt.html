The Kraken2 Cache Hunt

we set out to show that a 4-way set-associative hardware cache makes kraken2 faster. three agents argued about it, a simulator and a real server tested it, and the best result came from a place nobody was looking. this page tells the story in ten chapters. every picture moves, and every number comes from a file in the repo.

chapter 1 of 10

What kraken2 does all day

a nanopore sequencer gives you reads, long strings of the letters A, C, G and T. kraken2 answers one question about each read: which organism did this come from? it slides a small window along the read, keeps a short fingerprint called a minimizer from every window, and looks each fingerprint up in a giant table that says which organisms contain it.

that table is between 8 GB and 104 GB. every lookup jumps to a random place in it, so the computer has to fetch a fresh chunk of memory from DRAM, the slow main memory. millions of random jumps per run is where the time could be hiding, so that is where we started.

so what kraken2 is mostly a machine for making random memory trips. anything that makes those trips cheaper, or avoids them, makes it faster. that is the whole reason a cache was worth trying.
chapter 2 of 10

The idea: a cache that remembers answers

a cache is a small, fast memory that keeps recent answers close to the processor. if the answer you need is in the cache, that is a hit and it is quick. if not, that is a miss and you pay the full trip to DRAM. a modern chip stacks three caches, each bigger and slower than the last.

what "4-way set-associative" means

a cache cannot let any answer sit anywhere, because searching everything would be slow. so each address is assigned to one set, and a set has a few slots called ways. in a 4-way cache a set has 4 slots. when a fifth address arrives for the same set, one resident has to leave. the rule for who leaves is the eviction policy; LRU means "evict the one used longest ago". watch it work:

the hypothesis a 4-way hardware cache, or a 4-way software cache kraken2 builds for itself, might hold the right recent answers and save trips to DRAM. that is what we tried to prove.
chapter 3 of 10

Testing without owning the hardware: Sniper

you cannot resize the cache on a real chip. Sniper is a simulator: it runs the real kraken2 program instruction by instruction on a pretend processor whose caches we can set to any size and associativity, then reports cycles, hit rates and instructions. we built it on Luna in September and fixed several bugs to make it load our configs.

chapter 5 of 10

Why nothing held up

an auditor agent recomputed every row of every results file. the arithmetic was clean (189 of 190 rows matched, the one flag was rounding). the problem was what the simulator was measuring, not the sums. four suspects:

suspect 1: the "no cache" binary was a different program

S0 and the cache builds were compiled from different source snapshots. S0 executes many more instructions, and the gap grows with database size, while the cache builds sit near 52 M. cycles were nearly identical (within about 2%) for 1 to 16 ways and for cache sizes from 128 KB to 64 MB, so the cache was not the cause of the "2x".

suspect 2: the simulated LLC was tiny

with one simulated core (-n 1) Sniper builds a single slice of the last-level cache, about 1.1 MB, not Luna's real 105 MB.

suspect 3: the windows were tiny and cold

10 to 500 reads touch each part of the table about once. there was never time for repeated lookups to build up, so steady-state reuse was never measured. a real run has 1.87 million reads.

suspect 4: the pretend machine is too cheap

there was also no prefetching, no hugepage or TLB model, no thread contention, and no calibration against the real perf counters.

verdict both the "wins" and the "nulls" from Sniper are weak evidence about Luna. the one thing the real machine had already shown independently was that the software cache is worth nothing in production (the S6 ablation: 11.06 s with it, 11.10 s without).
chapter 6 of 10

Three agents argue it out

you asked for three agents that argue and reach a conclusion. we ran five rounds. round 1 read the history, round 2 argued why nothing was positive, round 3 researched papers and ideas, round 4 voted, round 5 ran experiments on Luna. here is round 2:

agent A: "the null is real"reuse exists but is too far apart for any affordable cache. my first claim of "near-zero reuse" was wrong: 90.7% of lookups repeat. but 81% of the repeats are 10 thousand to a million lookups apart.
agent B: "the simulator is broken"one 1.1 MB slice, uncalibrated memory, cold windows. the setup could not have shown a win even if one exists. calibrate against perf first.
agent C: "wrong layer"every cache change was null on Luna. every access-pattern or page-size change was a real win (S14 hugepages 35 s to 13-20 s, S16 prefetch -10%). stop caching, start hiding latency.

round 3 searched for real papers (RRIP, SHiP, Hawkeye, TinyLFU, group prefetching, AMAC, PTHash and more; the reports mark which citations were opened and which are unverified). round 4 was the cross-examination. they attacked each other's arithmetic, retracted weak ideas, and voted:

what the debate fixed double hashing was predicted to touch 60% more cache lines, break-even must use measured memory time not a guessed 90 ns, and the old "one cache line per set" SIMD idea needed two lines because entries are 24 bytes.

chapter 8 of 10

The ceiling, and double hashing

a hit rate is only half the story. a cache can save at most the time spent on lookups. we profiled stock S19 with perf on three databases. the lookup functions (PrefetchIndex and GetAt) were only 7.7% of CPU samples on 8 GB and 6.9% on 16 GB. GetAt, where the memory wait would show, was under 1%, because S19's prefetching already hides most DRAM latency.

try the calculator. the best possible speedup is 1 divided by (1 minus lookup share times hit rate):

conclusion for eviction policy on the 8 GB and 16 GB databases no policy can give more than about 3 to 5%. a new eviction policy is not where a noticeable speedup lives, once S19's prefetching is in.

structbench: why double hashing loses

thesis 2 wanted to switch from linear probing to double hashing, because double hashing needs fewer probes when the table is full. we built a stand-alone benchmark with the real kraken2 rule (step = (hash >> 8) | 1), 4-byte cells, load 0.70 and S16-style prefetch. a cache line holds 16 cells. linear probing walks along cells that share a line. double hashing hops to a new line every probe:

two honest side notes. first, the first version of this benchmark had a bug (the fingerprint and the start slot used the same hash bits, so 43% of absent keys falsely matched); we caught it from the hit counts and fixed it before reporting anything. second, with double hashing one insert failed at two table sizes. capacities of the form 2^k minus 1 divide by 3, so a step that is a multiple of 3 visits only a third of the table. real kraken2 capacities are arbitrary, so that silent-failure risk needs checking before anyone ships double hashing.

for thesis 2 keep linear probing for speed. double hashing is a space and false-positive trade, and it costs 1.8 to 2.5x on lookup time.

chapter 10 of 10

Scoreboard and what to ask next

open threads

  • the 103 GB profile at one thread was dominated by database loading, so the 28%-of-user-time lookup share there is rough. AMAC (deeper latency hiding) is still unmeasured. at production scale GetAt is 6.7% and PrefetchIndex 9.7%, so it could still matter on the biggest database.
  • the scanner (NextMinimizer 19% and ClassifySequence 17%) is now the largest cost. S21 compile-flag variants exist on Luna but were not part of this work.
  • the Sniper side still needs calibration against perf, a full-size LLC, and honest-scale windows before it can support any claim.
glossary: every term, from zero

read: one DNA fragment from the sequencer, thousands of letters long. minimizer: a short fingerprint picked from each window of a read. hash table: a big array where a fingerprint's hash picks the cell to check. cache: small fast memory holding recent answers. hit / miss: found in cache / not found. associativity (N-way): how many slots one address may use inside a cache. eviction policy: the rule for which resident leaves, for example LRU (least recently used). Belady: the perfect policy that knows the future, used as an upper bound. LLC: last-level cache, the biggest cache (L3). DRAM: main memory. prefetch: asking memory for data before it is needed, so waiting overlaps. cycles / IPC: processor clock ticks / instructions per tick. linear probing: on a collision, try the next cell. double hashing: on a collision, jump by a hash-dependent step. perf: the Linux profiler that samples where a program spends time. HyperLogLog: a compact counter that estimates how many distinct items were seen. S0, S19: our names for stock kraken2 and the version with all our speedups.
