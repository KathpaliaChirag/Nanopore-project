The Kraken2 Cache Hunt

we wanted to make a DNA-sorting program faster by giving it a smarter memory shortcut. it did not work the way we hoped. along the way we found something better. this page explains every step in plain words, with pictures that move. you do not need any background.

the 60 second version

  1. the program: kraken2 reads DNA and decides which living thing it came from. to do that it looks things up in a gigantic list, millions of times. each lookup is a slow trip to far-away memory.
  2. our idea: keep a few recent answers close by, like books on a desk, so we skip some trips. this shortcut is called a cache.
  3. first results: in a computer simulator the shortcut looked great on small jobs, then stopped helping on bigger ones.
  4. the check: we tested the test itself. the simulator could not be trusted for the real server, so we measured on the real server instead.
  5. the real server said: lookups do repeat, but even a perfect shortcut would save only 3 to 5%. a second idea, called double hashing, made lookups about 2 times slower.
  6. the surprise: the program was doing extra counting that nobody asked to see. removing it with one line made real runs 1.06 to 1.64 times as fast, with the same answers.

chapter 1 of 10

What kraken2 does all day

in one sentence: kraken2 looks up millions of small fingerprints in a huge list, and each lookup is a slow trip.

a DNA sequencer hands us a read, a long string of the letters A, C, G and T. kraken2 answers one question about it: which living thing did this come from, a bacterium, a human, something else?

to find out, it slides a small window along the read and takes a short fingerprint from each window (the technical name is a minimizer). then it looks each fingerprint up in the table, a list that says which organisms contain that fingerprint.

think of it like a phone book. you have a name (the fingerprint) and want the number (the organism). the problem is the phone book is enormous, so it is kept in a far-away warehouse, and every lookup means a trip to fetch one page.

the table is between 8 GB and 104 GB, far too big to sit next to the processor. it lives in the computer's main memory (called DRAM). each lookup jumps to a random page of it. one trip takes about 100 nanoseconds. that sounds tiny, but kraken2 makes hundreds of millions of trips, so they add up.

in plain words kraken2 spends its time making slow trips to a giant list. fewer trips, or faster trips, means a faster program. that is why we looked at caches.
chapter 2 of 10

The idea: keep a few answers close

in one sentence: a cache is a small shelf of recent answers, so repeat questions skip the long trip.
think of it like studying. you keep the books you are using on your desk. when you need one, you check the desk first. if it is there, you are done in a blink. if not, you walk to the shelf in the room, then the library downstairs, and in the worst case to a warehouse across town.

a computer works the same way. when the answer is already on the shelf, that is a hit (fast). when it is not, that is a miss (slow, go one level further). a chip has three shelves, each bigger and slower than the last, and then the warehouse, which is the main memory.

what does "4-way" mean?

a desk cannot hold every book, so it needs rules. one simple rule: every book has an assigned drawer, and each drawer holds a few books. the number of books per drawer is called the associativity. in a "4-way" cache, each drawer holds 4.

when a fifth book belongs in a full drawer, one has to go back. the rule for who goes is the eviction policy. the most common rule is LRU: send back the one you have not touched for the longest time. watch one drawer work. the letters are books arriving in order.

our guess if we pick the right drawers and the right rules, many lookups will find their answer nearby and skip the warehouse trip. we set out to prove that a 4-slot drawer works best.
chapter 3 of 10

Testing without owning the machine

in one sentence: we used a simulator, a flight simulator for chips, because we cannot rebuild a real chip.

we cannot change how big a real chip's desk is or how many books fit in a drawer. so we used a simulator called Sniper. it runs the real kraken2 program on a pretend chip, where we can set any desk size and any drawer size. when it finishes it reports how many clock ticks (called cycles) the job took. fewer ticks means faster.

think of it like a flight simulator. pilots can try dangerous things without a real plane. we can try odd cache designs without a real chip. the catch is the same too: a simulator is only as good as the model inside it.
remember this the simulator could only run a sliver of a real job. later this turns out to matter a lot.

for the curious: what the speedup numbers mean exactly

speedup is cycles of the baseline divided by cycles of the variant, measured in the simulator, never by a stopwatch. an early version of our charts used the simulator's own run time by mistake, which only measures how slow the simulator is. we caught this and recomputed everything from cycles.

so far "4 per drawer wins on big databases at small jobs, loses at larger jobs, and the hardware drawer size does nothing." before believing any of it we checked the experiment itself.
chapter 5 of 10

Why we could not trust it

in one sentence: the arithmetic was right, but the test was set up in ways that made the results meaningless for the real server.

we asked an "auditor" agent to recompute every number in every results file. the sums were fine (189 of 190 rows matched, and the one miss was rounding). the problem was what the test measured. here are the four suspects.

suspect 1: we compared against a different program

the "no cache" program (S0) was built from a slightly different copy of the code. it did extra work that had nothing to do with caches, and the extra work grew with database size. so "the cache made it 2x faster" mostly meant "the old program was doing more instructions".

suspect 2: the pretend library was tiny

with one simulated core, Sniper builds only one small slice of the big last-level cache. that is about 1.1 MB, while Luna's real one is 105 MB.

suspect 3: the sample was too small

think of it like judging a restaurant by watching one table for 30 seconds. we ran 10 to 500 reads. a real run has 1.87 million. in so short a run nearly every lookup is new, so we never saw what happens once lookups start repeating.

suspect 4: the pretend machine was too forgiving

it also had no prefetching (asking memory for data early), no model of page tables, no several-cores-fighting-over-memory effects, and it was never compared against the real machine's own counters.

in plain words both the "wins" and the "no effects" from the simulator are weak evidence about the real server. the one solid fact we already had from the real machine: the software cache made no difference in production (11.06 seconds with it, 11.10 without).

Three agents argue it out

in one sentence: three AI agents took opposite positions, attacked each other's numbers, and voted on what to test.

you asked for three agents that argue and reach a conclusion. we ran five rounds. round 1 reviewed what had been done. round 2 argued why nothing worked. round 3 searched for papers and ideas. round 4 cross-examined each other and voted. round 5 ran the winning ideas on the real server. here is round 2, where each agent defended a different explanation:

agent A says: "the null is real"the same lookups do repeat, but too long apart for any affordable cache to remember. my first claim of "almost no repeats" was wrong, because 9 in 10 lookups are repeats. the catch is that most repeats come after hundreds of thousands of other lookups.
agent B says: "the simulator is broken"one tiny slice of cache, made-up memory speeds, and samples too short to see anything. even if a real win existed, this setup could not have found it. check it against the real machine first.
agent C says: "wrong place to look"on the real machine every cache change did nothing, while every change to the order or timing of memory requests helped (huge memory pages: 35 s down to 13 to 20 s). stop caching and hide the waiting instead.

in round 3 they searched for real research papers (replacement policies called RRIP, SHiP and Hawkeye, a frequency filter called TinyLFU, prefetching tricks called group prefetching and AMAC, and compact table designs). the reports mark which papers they actually opened and which are unverified. in round 4 they voted. here are the picks, 1st being the top priority:

chapter 7 of 10

Do the same lookups repeat?

in one sentence: yes, a lot, but a repeat usually comes long after the first lookup.

a cache only helps if you ask for the same thing again. so on Luna we recorded the table address of every single lookup during a real run: 104,980 reads against the 8 GB list, 12,237,762 lookups in total. then we counted.

result: those 12 million lookups touched only 2,270,742 different spots. so more than 4 out of 5 lookups (81%) went to a spot we had already visited.

a few popular spots cover most lookups

but the repeats are far apart

when a spot is visited again, how many other spots were visited in between? that gap matters, because a small cache forgets old entries when it fills up.

so what would a cache actually catch?

we replayed the recorded lookups through imaginary caches of different sizes. "perfect" is a cache that magically knows the future and always keeps the right entries, so no real rule can beat it.

for the curious: how the trace was made

we copied the fastest version of our code (called S19) into a separate folder, added a few lines that write the table slot number and a hit flag for every lookup into memory, ran it, and then analysed the file offline with a short C++ program. the classification output was unchanged (101,922 reads classified, 97.09%) and the logging cost about 3%. the files are in e1/ in the repo.

in plain words there is plenty of repetition, and a cache of a few megabytes could catch 4 lookups in 10. so a cache looks useful. the next question is whether that actually saves enough time.
chapter 8 of 10

How much could a cache ever save?

in one sentence: you can never save more time than the part of the job you speed up takes in the first place.
think of it like a delivery job where 8 minutes out of every 100 go to fetching packages from the warehouse. even if you make every fetch instant, you can save at most 8 minutes. and a cache only helps on the fetches it catches, say 4 out of 10. so the real saving is about 8 x 0.4 = 3 minutes, or 3%.

to find the real share, we used perf, a profiler that peeks at the running program thousands of times a second to see what it is doing. it showed that table lookups take only about 7.7% of the time on the 8 GB list and 6.9% on the 16 GB list. the part where the program actually waits for memory was under 1%. that is because kraken2 already asks memory for pages ahead of time (called prefetching), so most of the waiting is hidden.

conclusion for smarter caching on the 8 GB and 16 GB lists, no replacement rule can save more than about 3 to 5%. once kraken2 already hides its memory waits, there is not much left for a cache to fix.

the second idea: double hashing

thesis 2 wanted to try something called double hashing. first the problem it solves. when you put a fingerprint in the table and its spot is already taken, you must pick another spot. there are two common ways.

think of it like a car park. your usual space is taken. linear probing says: try the very next space, which is in the same row. double hashing says: jump by a personal step size to a space far away, in a different row. the far jump finds a free space in fewer tries when the car park is nearly full. but memory arrives in rows of 64 bytes, and fetching a new row is the slow part. so more row changes means more slow trips.

we built a small stand-alone test that copies kraken2's exact rules (cells are 4 bytes, the table is 70% full, lookups are prefetched, and 13% of the lookups are for things not in the table, like the real data). the numbers are nanoseconds per lookup for one thread. a smaller number is faster.

for the curious: two honest side notes

first, our first version of this test had a bug. it used the same bits of the scrambled number to choose the starting spot and to make the "name tag" stored in each cell, so 43% of missing items falsely matched. we spotted it because the found-share was far too high, fixed it, and reran everything. every number above is from the fixed version.

second, with double hashing one insert failed at two of the table sizes. table sizes of the form 2^k minus 1 divide by 3, so a jump size that is a multiple of 3 only visits a third of the spots and can run out of room. real kraken2 table sizes are arbitrary, so the risk exists there too and should be checked before anyone uses double hashing for real.

for thesis 2 keep linear probing if you want speed. double hashing may still be useful for saving space or lowering false matches, but it costs about 2x on lookups.

chapter 10 of 10

Scoreboard and what to ask next

in one sentence: the cache story is mostly a "no", and the best win came from profiling the real run.

what is still open

  • on the 103 GB list the profile was mostly database loading in our single-thread test, so the lookup share there is rough. asking memory even earlier (AMAC) is still untested and could matter on the biggest database, where the lookup is about 16% of the time at 32 threads.
  • after our fix the biggest remaining costs are the part that scans the read for fingerprints (19%) and the part that scores the answer (17%). other people on the team tried compiler tricks on that already.
  • the simulator still needs a proper check against the real machine, a full-size cache and bigger samples before anyone should quote it.
glossary: every term, with a comparison

read: one DNA fragment from the sequencer, thousands of letters. fingerprint (minimizer): a short code picked from each window of a read, like a name to look up. table: the giant list that maps fingerprints to organisms, like a phone book. DRAM / main memory: the warehouse. big and slow. cache: a small, fast shelf of recent answers. L1, L2, L3: desk, shelf in the room, library downstairs. hit / miss: found nearby / had to go further. drawer / way / associativity: how many entries fit in one assigned slot group. "4-way" means 4. eviction policy: the rule for who is sent away when a drawer is full. LRU: send away the one not used for the longest time. perfect (Belady): the imaginary rule that knows the future, the best possible. prefetch: asking memory for a page before you need it, so the waiting overlaps with other work. cycles / IPC: processor clock ticks, and instructions done per tick. simulator (Sniper): a pretend chip you can reshape. profiler (perf): a tool that samples what a program is doing to see where time goes. linear probing / double hashing: the next car space versus a far jump when a space is taken. HyperLogLog: a compact counter that estimates how many different things were seen. S0, S19: our names for stock kraken2 and the version with all our speedups. speedup: how many times as fast, so 1.64x means 20 seconds becomes 12.
