# round 3, agent C: methodology and memory-level parallelism, what can still give a positive result

scope: read-only. read all round 1 and round 2 files, then ran web searches. nothing run on luna, nothing else in the repo changed. "seen" below means the title, authors, venue and abstract appeared in search results or a fetched page; i did not read full texts. "unverified" means i could not confirm it.

## 0. one-paragraph position

round 2 left one open question that decides everything: can sniper, as configured, see the effects that real luna already measured (S9 batched prefetch 1.14x on 103GB, S14 hugepages 1.25 to 1.30x on 8 and 16GB, S16 pipelined prefetch 1.10x on 103GB)? nobody has tested that. if sniper cannot reproduce known real wins, it cannot be trusted for any new idea, and the next move is real-hardware tools (CAT, perf) plus a trace-driven model. if it can, the layout and mlp track is open in the simulator. the three experiments at the end are built to answer that in under two weeks, cheapest first.

## 1. how sniper models the things that matter (what i could confirm)

- core model. sniper is an interval simulator: it jumps between miss events and models memory-level parallelism (MLP) as a second-order effect. source: Carlson, Heirman, Eeckhout, "Sniper: Exploring the Level of Abstraction for Scalable and Accurate Parallel Multi-Core Simulation", SC 2011, https://www.doi.org/10.1145/2063384.2063454 and https://www.comp.nus.edu.sg/~tcarlson/pdfs/carlson2011etloafsaapms.pdf (seen). validated against a 16-core Xeon X7460 with about 25% average error on 16 thread apps (seen in slides, so error bars of 25% are normal for sniper even when validated).
- rob window. a later paper adds an instruction-window-centric model that simulates the rob explicitly, released in Sniper 6.0: Carlson, Heirman, Allam, Kaxiras, Eeckhout, "An Evaluation of High-Level Mechanistic Core Models", ACM TACO 2014 (venue and authors from my memory of the search slides at https://www.comp.nus.edu.sg/~tcarlson/presentations/carlson2014aeohmcm.slides.pdf; author list unverified). consequence: which core model the luna config selects (interval vs rob) decides how overlap of independent misses is computed. check `core/core_model` in the cfg.
- mshr and tlb. the current github master memory_manager.cc (fetched) reads an `outstanding_misses` key per cache level ("L1-D limits its own misses, L2 the misses that go past it") and creates a memory management unit that performs address translation and counts dram accesses during page walks. so master has mshr limits, tlb plus page walk with dram traffic, and a page-fault path. whether the sniper build used in this project is that version is unknown. action: grep the installed config tree for `outstanding_misses` and `perf_model/mmu` keys. if both exist the instrument has the right knobs for S14 and S16, only never tuned.
- software prefetch instructions. this is the key unknown and i could not settle it. evidence: (1) sift_format.h (fetched) has no prefetch record or instruction class, only size, address count, branch bits and addresses. so a prefetch is either dropped, or arrives as an ordinary memory read. (2) a student report, https://johnpaulharriman.github.io/report.html (seen), says they "cannot be entirely sure" sniper executes their prefetch instructions, saw no change between prefetch and no prefetch runs, and notes sniper counts overlapping misses as hits. anecdotal, not authoritative. (3) sniper mailing list thread https://groups.google.com/g/snipersim/c/yPrT4HN-9ZU (seen): a prefetch in flight makes a later access see a "hit" with extra delay until the fill completes. that is about the hardware and instruction prefetch path, but it shows the memory system does model in-flight fills. conclusion: unknown, probably treated as a plain load at best. a plain load at the rob head blocks retirement, a real prefetch does not, so even in the best case sniper under-credits S9 and S16. the microbenchmark in section 5 settles it.
- hardware prefetchers. kraken2 probes are random; hardware prefetch does not matter for lookups. it matters for the load phase and read parsing. skip.
- dram. sniper default is one fixed latency plus a bandwidth cap (cleanstart: 45 ns, 57.6 GB/s). measured sapphire rapids is about 107 ns dram and about 33 ns (125 cycles at 3 GHz, 88 in a small cluster mode) l3, Chips and Cheese, https://chipsandcheese.com/p/a-peek-at-sapphire-rapids (seen in results; luna's exact xeon model is not recorded here, so treat as same class not same chip). so the sim dram is about 2.4x too cheap, and the 35 cycle nuca hit is about 3x too cheap. this error scales every stall term.

## 2. sampled simulation and roi markers (fix for tiny cold windows)

- SMARTS: Wunderlich, Wenisch, Falsafi, Hoe, "SMARTS: Accelerating Microarchitecture Simulation via Rigorous Statistical Sampling", ISCA 2003, DOI 10.1109/ISCA.2003.1206991, https://www.doi.org/10.1145/1147224.1147225 is the journal-era page (seen; abstract says CPI within 3% at 99.7% confidence from fewer than 50M measured instructions per SPEC benchmark). method: many short detailed windows, functional warming of caches and predictors between them, confidence interval from the window variance.
- SimPoint: Sherwood, Perelman, Hamerly, Calder, "Automatically Characterizing Large Scale Program Behavior", ASPLOS 2002. unverified (only seen as a bibliography entry). picks representative phases by basic-block vectors.
- what it would let us claim: steady-state per-lookup cost and cache behavior at production read counts, with a stated confidence interval, instead of a 10 to 500 read cold window. this removes B's strongest point (cold llc, 76K to 2.3M unique lines vs 1.68M llc lines).
- cost: roi markers around the classification loop (sniper has SimRoiStart/SimRoiEnd magic ops; whether the sde frontend used here honors them needs checking, unverified), a way to warm caches over a skipped region, 10 to 20 windows of 20 to 50M instructions at about 200 to 230 KIPS is 25 to 70 minutes of wall time per window. total 1 to 2 days per variant.
- needs on luna: nothing new if sniper runs where it runs now; needs a checkpoint or trace of the load phase so windows start after the table is resident.
- kill: if warmed windows disagree with each other by more than 10% in cycles, the workload is not stationary at this scale and sampling gives no claim.
- honest note: the sde frontend produces a linear trace, so true fast-forward is only possible by skipping trace records. warming by replaying only the memory ops of the skipped span through the cache model is the usual workaround (functional warming, as in SMARTS). implementation effort unknown.

## 3. trace-driven and reuse-distance tools (fix for "no reuse at tested scale")

- reuse (stack) distance gives a miss-ratio curve for every cache size from one pass. Waldspurger et al., "Efficient MRC Construction with SHARDS", USENIX FAST 2015, https://www.usenix.org/conference/fast15/technical-sessions/presentation/waldspurger (seen): hash-sample addresses at under 1%, error under 0.01 in miss ratio with about 1 MB of state. survey: Byrne, "A Survey of Miss-Ratio Curve Construction Techniques", https://arxiv.org/pdf/1804.01972 (seen).
- tracing real address streams. DynamoRIO drcachesim collects memory traces, has online and offline modes, a configurable cache and a TLB simulator, a miss file, and a reuse-distance tool, https://dynamorio.org/sec_drcachesim_tools.html (seen). Intel SDE is Pin-based, https://www.intel.com/software/sde (seen; already the sniper frontend here). `perf mem` and PEBS sampling are alternatives for real-hardware address samples; i did not search them separately, treat as unverified for this use.
- what it would let us claim: the exact llc miss-ratio curve of kraken2 lookups at 1e5 reads, which settles "is there reuse" for every llc size at once, independent of sniper's timing model. a hit rate is a property of the trace, so this is the one analysis that A and B both accept.
- cheapest route for kraken2 specifically: do not trace the binary at all. add a 5 line patch that appends the table slot index (8 bytes) for each probe to a buffer. 1e8 probes is under 1 GB. then run SHARDS or exact stack distance in a separate program. no pin overhead, no sniper.
- cost: 1 day patch plus capture on luna, 1 day analysis. needs one luna run on 8GB db with 1e5 reads (minutes natively).
- kill: if the miss-ratio curve is flat at 80 to 85% miss from 1 MB to 105 MB, no llc-size or eviction idea can help at that db size; stop thesis 1 lookup-cache claims for db sizes above the llc. this matches the perf counters (80 to 84% llc miss on 8GB), so i predict this outcome for 8GB and above, and a real knee only for DBs near the llc size (the 50MB db).

## 4. calibration against perf counters, and real-hardware cache size control

- calibration recipe (from B round 2, restated with literature support): run one binary natively under `perf stat`, run the same input under the simulator, accept if instructions within 2%, cycles within 15%, llc misses within 20%, dtlb misses within 25%. the only literature example i found is a ZSim plus DRAMsim2 memory-latency validation on a Sandy Bridge E5-2670 that found about 20 ns missing and 55% of real latency (found via search at https://par.nsf.gov/servlets/purl/10085414 and https://core.ac.uk/download/185529443.pdf, which of the two is that paper is not confirmed, unverified). take-away: latency microbenchmarks first, counters second.
- CAT and resctrl. the linux kernel documents Intel RDT through resctrl: `cat_l3` flag, a capacity bitmask per resource in `info/L3/cbm_mask`, `min_cbm_bits`, schemata per cache domain, and llc_occupancy and mbm_total_bytes monitoring under L3_MON, https://docs.kernel.org/filesystems/resctrl.html (seen). pqos (intel-cmt-cat) usage unverified.
- cache pirating, the no-root fallback and the classic method: Eklov, Nikoleris, Black-Schaffer, Hagersten, "Cache Pirating: Measuring the Curse of the Shared Cache", ICPP 2011, DOI 10.1109/ICPP.2011.15, https://www.it.uu.se/research/group/uart/measurement/shared_resource_sensitivity/cache_pirate.html (seen; author order unconfirmed). a pirate thread steals a controlled amount of shared llc while counters measure the target. 5.5% overhead on Nehalem.
- what CAT would let us claim: measured kraken2 runtime and llc miss rate versus llc capacity (about 7 MB steps if 15 ways of 105 MB), on the real machine, no model. this is the only experiment where the result cannot be a modelling artifact.
- cost: 2 to 3 days. needs root on luna, `grep -o cat_l3 /proc/cpuinfo`, `mount -t resctrl resctrl /sys/fs/resctrl`, and a quiet machine (shared box, noise). caveats: CAT limits ways not sets, so very small masks raise conflict misses beyond the capacity effect; private l2 (2 MB per core) is not restricted, so the curve starts above l2; only a contiguous mask is legal; two sockets have separate masks (`L3:0=..;1=..`), pin with numactl.
- kill: no `cat_l3` flag or no root. fallback is a pirate thread, or one thread per core with a streaming buffer that holds a fixed footprint in the llc. if the 50MB db shows under 3% change from 105 MB to 14 MB of llc, lookups are not cache-capacity limited even where the table fits, and the llc-aware idea has no headroom.

## 5. mlp, group prefetching, amac, coroutines (the layer the data points at)

these are the published versions of what S9 and S16 already do on luna. they matter for this report because they give model forms and expected gain.

- Chen, Ailamaki, Gibbons, Mowry, "Improving Hash Join Performance through Prefetching", ICDE 2004, pp 116 to 127, https://www.pdl.cmu.edu/ftp/Database/icde04.pdf (seen). group prefetching and software-pipelined prefetching. hash join stalls over 73% of user time on cache misses; 2.0 to 2.9x speedup of the join phase. kraken2 S9 is group prefetching, S16 is software pipelining. the paper's own model says the group size needs about (latency / work per element) in flight, which predicts S9's gain saturates early (K2_B 16 to 64 within 0.6%, matches the real null).
- Kocberber, Falsafi, Grot, "Asynchronous Memory Access Chaining", PVLDB 9(4), 2015, pp 252 to 263, DOI 10.14778/2856318.2856321, https://dblp.dagstuhl.de/rec/journals/pvldb/KocberberFG15.html (seen). per-lookup state machine, new lookup starts when any in-flight one completes; up to 2.3x over prior prefetching on irregular lookups. relevance: kraken2 probe chains have variable length (1.07 hit lines, 1.32 miss lines at load 0.70), so lockstep group prefetching leaves bubbles that AMAC fills. predicted extra gain over S16 on 103GB: 5 to 15%, my estimate, not measured.
- Jonathan, Minhas, Hunter, Levandoski, Nishanov, "Exploiting Coroutines to Attack the Killer Nanoseconds", PVLDB 11(11), 2018, DOI 10.14778/3236187.3236216 (seen via search; up to 3x on tree probing as cited by CoroBase https://arxiv.org/pdf/2010.15981). Psaropoulos, Legler, May, Ailamaki, "Interleaving with Coroutines: A Practical Approach for Robust Index Joins", PVLDB 11(2), 2017, pp 230 to 242, DOI 10.14778/3149193.3149202, https://infoscience.epfl.ch/record/231318 (seen). coroutines equal AMAC in performance with less code change. kraken2 would need C++20 coroutines or hand-written stages; the existing S16 structure is already close.
- what it would let us claim: a named, literature-grounded latency-hiding design for kraken2 lookups with measured gains over S16 on luna, plus the observation that no published metagenomic classifier does this (partial check only, see below).
- cost: AMAC variant of the lookup loop 2 to 3 days to write and verify byte-identical output, 1 day to bench. needs luna only.
- kill: under 3% over S16 at 103GB and 16GB across 3 reps (thp variance on luna is 13 to 21 s at 103GB, so use alternating runs).
- k-mer classification neighbors (seen in search): MetaCache-GPU, Kobus and Muller, https://arxiv.org/pdf/2106.08150 (multi-value GPU hash table, reports over two orders of magnitude over Kraken2 on GPU with index in gpu memory; the GPU hides latency by massive thread count, the same principle as AMAC). MegIS, Mansouri Ghiasi et al., 2024, https://arxiv.org/abs/2406.19113 (in-storage processing, 2.7 to 37.2x over performance-optimized software; attacks data movement of low-reuse data, which is our diagnosis). KrakenOnMem, a processing-in-memory accelerator for Kraken2 table lookups reporting up to 61.3% end-to-end speedup, and Sieve (in-dram) came up in a search snippet, https://par.nsf.gov/servlets/purl/10300825 (unverified which paper that is). GPMeta: not found in any search, unverified, do not cite until located. i found no source that applies software prefetch or amac to the kraken2 table in software; that is a gap, but my search was two queries, so say "i did not find" not "none exists".

## 7. TOP 3 EXPERIMENTS, ranked

### experiment 1: can sniper see S9 prefetch and S14 hugepage gains at all? (gate for the whole sniper track)

- hypothesis: on a 4 GB random-probe microbenchmark, sniper reproduces the ordering dependent chain >> independent probes > batched prefetch, and the S14 emulation (large-reach tlb) gives a gain similar to real luna.
- build: one C file, table 4 GB filled by real writes (not lazy zero pages), 2M random probes from a precomputed index array. variants: (a) dependent chain, 1 miss in flight; (b) independent probes, plain loads, ooo overlap only; (c) groups of 16, `__builtin_prefetch` all 16 then consume (S9 shape); (d) software pipelined, issue batch n+1 prefetch before consuming batch n (S16 shape); (e) variant c as a plain load into a dummy sum, "prefetch-as-load". each at 4 KB pages and, natively, at 2 MB (madvise) with the sim emulation by big tlb. one source lineage, one compile flag set, roi markers or a fixed warm-up of 200K probes excluded by differencing two sizes.
- run natively on luna with `perf stat` (cycles, dtlb_load_misses.walk_completed, llc misses) and in sniper with a flat 105 MB l3 and sapphire-rapids-class dram (107 ns) and l3 (about 100 cycles), plus the default config as a second row to show the effect of calibration.
- predicted native ns per probe on luna: (a) about 107 to 140, (b) 10 to 25 (10 to 12 line fill buffers overlap), (c) 7 to 15, (d) 6 to 13. c over b about 1.3 to 2x, 2 MB pages over 4 KB about 1.2 to 1.5x at 4 GB (a walk per probe at 4 KB; S14 measured 1.25 to 1.30x at 8 and 16GB). reasoning: line fill buffer limit, not the rob, caps (b); software prefetch retires immediately and frees the rob, so (c) beats (b).
- predicted sniper: if prefetch is dropped, (c) equals (b) within 5% and (e) is slower or equal to (b); if it becomes a plain load, (c) about (e), both limited by rob size; if modelled as a fill, (c) shows 1.3x or more.
- measure: ns per probe per variant, native vs sim, ratio of ratios; dtlb walks; dram reads per probe.
- runtime: 1 to 2 days (half a day to write and run natively, 1 day for sim runs, 2M probes at about 20 instructions is 40M instructions, under 5 minutes each).
- kill: if sniper's c/b ratio is inside 0.9 to 1.1 while native is at least 1.3, sniper is blind to prefetch, and the S9 and S16 style questions move to native-only plus the model in experiment 3. if sniper's (b) is more than 2x off native after dram and tlb recalibration, the mlp model is not usable and sniper is demoted to instruction-count and trace generation. if both match within 30%, the layout track in sniper is open and S14 plus S16 become the calibration targets from round 2 C.
- what it would let us claim: a one-page statement of what the simulator can and cannot represent, with numbers. this is a result in itself and it closes the A, B, C round 2 dispute with data.

### experiment 2: real-hardware llc size sweep with CAT (ground truth, no model)

- hypothesis: kraken2 runtime on a db that fits in the llc (50MB, and the small ESKAPE dbs) rises as llc capacity drops below the table size; on 8GB, 16GB and 103GB it is flat, because the table never fits and 80 to 84% of loads already miss.
- setup: stock kraken2 and S19 (two binaries, one lineage each), 1.87M reads, threads 8 and 32 pinned to one socket with numactl, resctrl group per mask: all 15 ways, 12, 8, 4, 2, 1 ways (about 105, 84, 56, 28, 14, 7 MB if 15 ways at 7 MB each; read `info/L3/cbm_mask` first, the real way count on luna is unknown). 3 repetitions, alternating order. record wall time excluding load, perf llc loads and misses, mbm_total_bytes from L3_MON, and kraken2 output hash (must stay byte-identical).
- predicted effect: 50MB db: no change from 105 to 56 MB, +8 to +30% at 14 MB and 7 MB. reasoning: lookup is 19.5% of cpu on 50MB (profile); if the table spills from llc (about 33 ns) to dram (about 107 ns) the lookup term rises up to 3x but prefetch hides part, so total +0.195 x (0.5 to 1.5) = 10 to 30%. 8GB to 103GB: within 3% from 105 to 28 MB, then a small rise at 14 and 7 MB from losing hot inner-table and metadata lines, under 6%. 4 vs 32 threads: sensitivity is larger at 32 threads because they share the llc and the 50MB table is touched by all.
- measure: time vs ways curve per db, llc miss rate vs ways, mbm bytes per read.
- runtime: 2 to 3 days including the 50MB and 8GB dbs only on day 1.
- kill: no `cat_l3`, no root, or luna is not quiet (run-to-run spread above 5%). then switch to the pirate method. also kill the claim if the 50MB db shows under 3% change at 14 MB: there is then no llc-capacity headroom at any db size and thesis 1 should say so. a positive curve on 50MB only would be a useful bounded result: "llc-aware sizing matters when the table is within 2x of llc capacity".
- what it would let us claim: the first measured llc-capacity sensitivity of kraken2 on the target machine. it is also the calibration curve for any later simulator llc sweep (the sim flat-l3 result should reproduce this curve's shape).

### experiment 3 (my own idea): trace once, fit a three-parameter mlp model, replay many layouts

- idea: stop asking the simulator for absolute time. split the problem. (1) the address stream is a property of the workload, capture it once at production scale with the 5 line probe logger from section 3. (2) hit and miss behavior for any llc size and tlb reach comes from one reuse-distance pass (SHARDS), no timing model. (3) time per probe is a small analytic model: t = (misses_llc x L_dram + hits_llc x L_llc + walks x L_walk) / MLP_eff, with three or four free constants (L_dram, L_walk, MLP_eff, fixed compute per probe) fitted to luna's existing measurements for stock, S9, S14 and S16 (their MLP and page settings differ, so the same constants must explain four runtimes). then hold out one db size: fit on 8GB and 16GB, predict 103GB.
- why it is new here: it uses real luna data as the calibration target (round 2 B step 0 asked for this but via sniper), sidesteps the 200 KIPS limit (the model replays 1e8 probes in seconds), and answers layout questions (bucketed table at one line per probe, bloom prefilter in front of the table, double hashing, 6-bit organism cell, mphf) by dram lines per lookup and overlap, which the round 2 C position says is the right dependent variable. layout variants only need their own probe-index function applied to the same minimizer stream, so no new trace per variant.
- hypothesis: the model with fitted constants predicts the held-out 103GB stock to S16 ratio within 15%, and ranks layout variants the same way luna does for the ones already built (S14 first).
- predicted effects to look for: bucketed or prefilter layout at load 0.70 cuts expected lines per lookup from about 1.07 to 1.0 on hits, and miss lookups from 1.32 to about 1.0 (or to 0 with a filter that fits in l3), for a model gain on miss-heavy streams of 10 to 25% of lookup time; double hashing changes line count little (1.0 to 1.2), expect under 5%. these are model predictions that real luna runs must then confirm; the claim is the validated method, not the layout numbers.
- measure: model error on held-out db, miss-ratio curve vs the experiment 2 CAT curve (cross-check), lines per lookup per layout.
- runtime: 5 days (1 day logger and capture, 1 day SHARDS and stack distance, 2 days fit and validate, 1 day layouts).
- kill: held-out error above 25%, or the model needs a different MLP_eff for every binary (then it explains nothing), or the logged stream's miss ratio disagrees with perf llc misses by more than 10 points (the trace is not the real stream). in any of those cases report it as a negative methodology result and fall back to real binaries only.

ranking logic: 1 is a day or two and decides whether sniper stays in the plan. 2 gives ground truth for the part of thesis 1 that sniper could never test, and can run in parallel with 1 (different people, different machines). 3 is the longest and only worth starting if 1 shows sniper is blind to prefetch and tlb, or as the main method if CK drops sniper for this layer.

## 8. what i could not settle

- which sniper version and core model the project uses (determines mshr, mmu and rob knobs).
- luna's cat support, way count, and exact xeon model (my latency figures are sapphire rapids class from Chips and Cheese, not luna).
- whether the sde frontend honors roi markers for sampled windows.

- big-db lookup share of cpu is still unmeasured (perf profile on 8GB, 2 hours); it sets the ceiling for every layout claim.

## summary (8 lines)

1. sniper models mlp through the interval or rob core model, mshr limits (`outstanding_misses`) and an mmu with page walks in current master; whether this project's build has those knobs is unchecked.
2. whether sniper executes software prefetch is unverified: the sift format has no prefetch record, a student report saw no effect, so it is probably a plain load or dropped; a 40M-instruction microbenchmark settles it.
3. sim dram (45 ns) and nuca (35 cycles) are about 2.4x and 3x too cheap against measured sapphire rapids class numbers (107 ns, 88 to 125 cycles), so recalibrate before reading any stall effect.
4. SMARTS-style sampled windows, SHARDS miss-ratio curves and a 5 line probe logger fix the cold-window and no-reuse objections without simulating 1e5 reads in detail.
5. group prefetching (Chen 2004), AMAC (Kocberber 2015) and coroutines (Jonathan 2018, Psaropoulos 2017) are the published form of S9 and S16; AMAC over S16 is a plausible extra 5 to 15% on 103GB, unmeasured.
6. CAT through resctrl is the cheapest real llc-size sweep; predict a rise only for the 50MB db (+8 to +30% at 14 to 7 MB) and flat curves for 8GB and above.
7. top 3: (1) sniper microbenchmark gate, 1 to 2 days; (2) CAT sweep on luna, 2 to 3 days; (3) trace once plus fitted three-parameter mlp model replaying layout variants, 5 days.
8. the positive result most likely to exist is a layout or latency-hiding one (lines per lookup, overlap, page reach), validated on luna; an llc-aware cache result is plausible only for tables within about 2x of llc size.
