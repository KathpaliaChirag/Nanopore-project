Simulating kraken2's cache hierarchy with Sniper on Luna

What we built

  • Sniper cloned and built on Luna, with a config read from the real machine (L1d 48 KB, L2 2 MB, shared LLC 105 MB)
  • The LLC modelled as per-core slices (1,125 KB, 15-way)
  • The real kraken2 binary traced through it, with cycles as the metric (never Sniper's own run time)

What we varied

  • A software cache inside kraken2: none, or 1, 4, 8, 16 ways
  • Hardware LLC associativity, 1 to 30 ways
  • Four databases, 50 MB to 103 GB
  • Workloads of 10 to 500 reads (one 2,000-read run)

The simulator cannot run a real job: a production run has 1.87 million reads. That is why every Sniper experiment used a tiny sample, and it matters for how far the results can be trusted (slide 3). The LLC slice size in this config was later found to be half of what it should be (about 2.2 MB, not 1.1 MB), because the config divided by 96 logical CPUs per socket instead of 48 physical cores.
