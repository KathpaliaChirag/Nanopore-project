# Research brief - planning S3 and S4 given today's findings (2026-08-26)

This is a forward-looking planning brief for a fresh session (no prior conversation context) to research and produce a concrete design plan for S3 (LLC-topology-aware sizing) and S4 (biology-dependent eviction), given real constraints discovered today. read [`plan_paper/HANDOVER_2026-08-26.md`](https://github.com/KathpaliaChirag/Nanopore-project/blob/main/plan_paper/HANDOVER_2026-08-26.md) first for full current state, then [`plan_paper/command_log.md`](https://github.com/KathpaliaChirag/Nanopore-project/blob/main/plan_paper/command_log.md)'s 2026-08-26 entries for the full data behind every claim below.

## The constraints S3/S4's design must work within (all empirically confirmed today, not theoretical)

1. **Two independent hard ceilings on cache size**, not one:
   - a *slowdown* cliff at ~1,048,576+ sets (>=64MB/thread), `thread_local` array zero-initialization/first-touch cost dominates, up to 22x slower.
   - a *crash* ceiling at ~262,144+ sets (16MB/thread) under multi-threading, segfault (exit 139), most likely glibc's static TLS allocation limit for `thread_local` arrays created per-OpenMP-thread, unrelated to total RAM available (16MB x 96 threads is about 1.5GB, trivial on a 503GB machine, yet it still crashes).
   - both point at the same underlying fix: `thread_local` should hold a *pointer*, heap-allocated once per thread on first use, not a static array. this removes both ceilings (heap allocation doesn't have the TLS budget problem, and can be sized/lazily-initialized more carefully to avoid the zero-init cost too).
2. **Eviction policy has a real, measured effect, independent of capacity**, and its value is *largest exactly where capacity is smallest*: a trivial "protect anything hit once" rule improved hit rate +25% at 4,096 sets but only +4% at 262,144 sets (data: `command_log.md`, 2026-08-26 "capacity x eviction-policy experiment" entry). this is real evidence, not a hypothesis, S4 has a validated starting point (a one-bit hit-flag), not a blank page.
3. **Absolute hit rates are still very low even at the best-measured configuration** (~1.5% at 262,144 sets, pinned). this project's own prior M5 finding (90.7% k-mer reuse) is in real tension with this, the current working theory (`command_log.md`) is that repeats exist but are separated by more distinct intervening minimizers than any tested capacity can bridge, i.e. a locality problem, not an absence of reuse. this needs either confirmation or a better explanation.
4. only `standard_8gb` and `pluspf_103gb` matter for real conclusions, `sample_targeted` is small enough (50MB, fits in Luna's 210MB LLC) to behave differently and has already produced at least one confirmed measurement artifact (a global-atomic-counter contention issue, unrelated to the cache itself, see `command_log.md`).

## What to research and produce a plan for

1. **The heap-allocated `thread_local` fix.** is there a standard, low-risk pattern for this in C++11 (the project's language standard) that avoids introducing new bugs (e.g., lazy-init race conditions, leaks on thread exit)? Kraken2's classify.cc is performance-critical, hot-path code, the fix needs to add minimal overhead per lookup (an extra pointer dereference is fine, a lock or repeated allocation checks on every call would defeat the purpose).
2. **S3's actual sizing formula.** given the two ceilings above (now with #1 potentially removed by the heap fix, but budget for the case where it isn't done in time), and given LLC-topology detection is the stated goal (S3.1-S3.3 in `planning/week4plan.md`), what does a real, defensible sizing rule look like? should it be a fixed fraction of detected LLC capacity divided by expected thread count? does the pinning experiment's finding (smaller capacity + smart eviction can rival larger capacity + dumb eviction) change how aggressively S3 should try to grow the cache at all, versus investing that engineering effort in S4 instead?
3. **S4's eviction policy design**, building on today's validated "protect on first hit" baseline. what's the next-cheapest increment beyond a binary hit-flag, a small saturating counter (2-3 bits) for approximate frequency? does the project's own M5 finding (90.7% reuse) or any cited prior art (`kache-hash`, `MegIS`, `MetaCache-GPU`, `GPMeta`, see project memory for this comparator list) suggest a specific, cheap eviction scheme worth adapting rather than inventing from scratch?
4. **Resolve the M5-reuse-rate vs. low-hit-rate tension directly.** is there a cheap instrumentation addition (e.g., logging the actual distance-in-lookups between repeat occurrences of the same minimizer) that would confirm or refute the "locality problem, not reuse absence" theory, before committing S4's design to that assumption?
5. **Produce a concrete week-ahead plan** (in the style of `planning/week4plan.md`'s sub-step tables) for S3 and S4 that incorporates all of the above, sub-steps, Design vs. Measured tags, fallback rules if a sub-step gets stuck, consistent with this project's established planning format.
