### Porting is not a flag-flip — Agent G's deepest finding

The single most concrete, load-bearing Round 1 contribution on this question: porting is a **real, non-mechanical merge**, not a drop-in. `kraken2_prefetch.patch` re-declares `last_minimizer`/`last_taxon` as fresh function-locals in the exact scope where Track A's S1.1 patch already promoted those same variables to `thread_local` — applied naively, this either fails to `patch -p1` cleanly (the surrounding code has been rewritten four times since: S1→S2→S3→S4.0) or, if forced, silently reintroduces a stock, non-persistent depth-1 cache, quietly undoing S1.1's fix. The resolution is mechanical (drop the patch's re-declaration, keep S1's `thread_local` state, thread the new `PfSlot pf[]` array alongside it) but real — roughly an hour of careful reconciliation, not a research problem. A genuine bonus found in the same pass: pass 1 already computes `MurmurHash3(minimizer)` once per lookup for the prefetch address — S4.0's own hash-mix fix wants the identical call for `S2SetIndex`. Merging these removes a duplicate hash computation either patch would otherwise pay alone.

Composing with the S2 cache is architecturally clean: nothing in the batching machinery requires every slot in a batch to be a real miss — the existing code already proves this via its own `last_minimizer`/`is_ambiguous()` skip logic. A minimal merge (cache-check added to pass 2's resolve step, mirroring how S2 already wraps `hash->Get()` today) has zero new thread-safety surface, since `pf[]` is a per-call stack array (OpenMP gives each thread its own frame) and S2's `thread_local` state is untouched by any of it.

**Engineering estimate (Agent G, itemized):** ~0.5–1 day to re-derive the patch against the current post-S4.0 tree; ~0.5 day correctness pass (byte-identical output/report, the same discipline every S-step has followed); ~0.25 day crash/stability check (lower risk than any Track A step so far — `pf[]` is a ~1–2KB stack array, nowhere near the static-TLS territory that caused the S2/S3 crash); ~1 day for the full DB × thread-count benchmark sweep, reusing S3.4's exact methodology. **Total: 2–3 days for a standalone, Luna-verified result; 3–4 if the S2-merge is attempted too.** This is comparable to a single S-substep, not a new research arc.

**Genuine independent convergence, strengthening confidence in the mechanism itself:** this project's own May 2026 analysis (`kraken2_get_optimizations_v2.md`'s "Patch 10 — coarse batched Get() with prefetch pipeline") designed essentially the same technique from first principles, reading Luna's own source and profiling data — and explicitly deferred it as *"speculative; design only... Phase-3... implement only if Patches 1–9 leave the v1 target unmet."* PREFETCH.md is best read as an independent author validating this project's own previously-shelved idea, on different hardware, with real numbers. That's convergent evidence the mechanism is sound, not a borrowed, unvetted one.

## Q1 — Is there a genuinely different eviction policy, not a refinement of pinning? [Verdict: two real candidates, both cheap, both structurally bounded by the reuse-distance data]

**7/7 consensus that no *large-scale systems* eviction algorithm (ARC, 2Q, LRU-K, CLOCK-Pro, TinyLFU's sketch) transplants meaningfully onto a 4-way, ≤4-candidate-per-set structure.** Every one of these assumes either O(1)-vs-O(n) tradeoffs that don't exist at n=4 (CLOCK), or ghost-list/history-buffer memory larger than the resident cache itself (LRU-K, 2Q, ARC), or a key universe far larger than what needs ranking (TinyLFU's Count-Min sketch — an exact per-way counter is strictly cheaper and more precise at n=4, a conclusion the prior 2026-08-27 debate already reached and this exercise independently reconfirms).

**Genuinely different, cheap, and worth trying if any more S4 work happens at all — recency (pseudo-LRU/CLOCK), not another frequency variant.** The disproven pinning result and the still-scoped saturating counter are both frequency-family (protect what's been hit). Pseudo-LRU is a different axis entirely: 2 bits/set of real hardware-cache-style state, cheaper than the already-shipped `was_hit` byte, and it structurally can't produce the exact failure mode diagnosed in the pinning reversal (a one-hit-wonder squatting on a slot indefinitely), because a stale entry naturally rotates out. This is arguably the strongest-fit prior art available, precisely because S2 is itself explicitly modeled on real N-way hardware caches — pseudo-LRU is the literal mechanism real L1/L2 caches use at this associativity.

**A second real, independently-corroborated candidate — worth stating as the single strongest concrete finding of the whole exercise: shift the lever from eviction to *admission*.** Two agents reached this from completely different evidence with no shared source. Agent C inferred it from Kraken2's own reuse-distance histogram (most repeats arrive too late for eviction-victim-selection to matter, so gating what gets *let in* is the only lever left with headroom). Agent G found *independent empirical confirmation on a real workload*: the same `mtp1` branch's own, unrelated lookaside-cache experiment measured that **63.4% of distinct minimizers appear exactly once**, consuming 29.9% of all lookups — *"letting them in pushes useful entries out, and no replacement policy can undo that, because by the time you are choosing what to evict the junk is already inside"* (`KRAKEN2_CHANGES.md:181`). Their fix — admit a first-time miss only probabilistically (1-in-n) so a minimizer must recur before earning a slot — is architecturally the 2Q/TinyLFU-doorkeeper idea, applied at the correct lever (admission, not victim ranking) for a structure this small. The prior 2026-08-27 debate rejected TinyLFU's *sketch machinery* on sound grounds (no bookkeeping room at n=4) but never separately evaluated admission control as its own, distinct mechanism — this is new ground, not a re-litigation.

**A structural ceiling that bounds the whole question, verified directly by this report against the primary source (resolving an internal Round 1 disagreement):** Agent A/B/C/D/E all cited the log's claim that *"81% of all repeats... land at distances of 10,000–1,000,000 lookups apart"* at face value; Agent F flagged that the two disclosed cumulative figures (`lt1e5`=341,228, `lt1e6`=978,748) don't arithmetically reconcile with an "81%" reading if interpreted as cumulative-from-zero counts (they'd imply only ~60% of repeats fall under 1e6 at all, let alone 81% specifically in the 1e4–1e6 band). **This report re-derived it directly: `lt1e5` and `lt1e6` are histogram bucket counts, not cumulative sums — `lt1e5` = repeats with distance in [1e4, 1e5), `lt1e6` = repeats with distance in [1e5, 1e6). Summed, 341,228 + 978,748 = 1,319,976, which is 81.3% of the ~1,623,537 total repeats (54% of 3,006,550 lookups) — an exact match to the log's own headline claim.** Agent F's doubt was reasonable given genuinely ambiguous variable naming in the log, but the underlying data does not contradict the 81% figure once the bucket semantics are worked out. The conclusion this number supports — any 4-way, capacity-bounded eviction policy has a low ceiling regardless of sophistication, because most repeats arrive well after any safely-tested capacity would have already cycled the entry out — stands confirmed, not just assumed.

### Recommendation on Q1

If any further S4 eviction-policy engineering happens, spend it on the admission-gate idea first (real, independently-corroborated, cheap, genuinely unexplored), pseudo-LRU second (cheapest, lowest-risk, directly on-point prior art) — not a decay-refined version of the disproven pinning family. Set expectations low regardless: the reuse-distance ceiling bounds the entire class of victim-selection policies, admission control included, though admission control is the one mechanism with a plausible path to mattering at this reuse-distance shape.

## Q2 — Does raising cache capacity deserve a second look? [Verdict: yes, one bounded re-sweep, no wall-clock payoff expected]

**7/7 consensus, confirmed independently by every agent via direct date/commit-order checking: both the 2026-08-26 size sweep and the 2026-08-30 S3.4 full-matrix benchmark were measured on the broken (pre-hash-mix) `S2SetIndex`.** S4.0's fix landed chronologically and causally after both. This is not a matter of interpretation — it's a plain date fact every agent verified the same way.

**Whether this changes the *shape* of the diminishing-returns curve, not just its starting point, is a real open question — and the evidence leans toward "probably not much, but untested."** A skewed hash (one set absorbing 225× average load) plausibly suppresses the *slope* of a capacity curve, not just its intercept — adding more sets to a bit-mask that ignores most of a minimizer's entropy doesn't fix the underlying clustering. This makes the 2026-08-26 sweep's specific "diminishing returns" shape suspect as a *property of the workload* — but it is genuinely unmeasured which way it breaks, not established.

**A structural ceiling nearly closes this question anyway.** The LLC-topology-aware sizing formula caps realistic capacity at 4,096–8,192 sets at the thread counts that actually matter for a submission number (32–96T) — and that exact regime was already re-tested post-hash-fix and came back null (`command_log.md:404`: "all four configs statistically indistinguishable... within noise" at T=32/T=96). **At the thread counts that matter for production, the capacity question is already closed, on the fixed hash, with a null answer.** The genuinely open combination — fixed hash × a *raised* capacity ceiling (up to 4,194,304 sets, already proven crash/slowdown-safe by S3.3) × *low* thread count (T=1/8/16, not yet tested post-fix) — has never been run and is cheap to test (a rebuild-and-rerun of existing infrastructure, no new engineering).

### Recommendation on Q2

Run the one specific untested combination — fixed hash, raised `S3_MAX_SETS` clamp, T=1/8/16 — as a half-day-to-one-day experiment. Expect a cleaner, more current hit-rate-vs-size table for the paper, not a wall-clock win: the same 8.9× hit-rate jump already measured at fixed capacity moved wall-clock by exactly zero, so there's no empirical reason to expect a further capacity-driven hit-rate gain to behave differently. ## Q5 — What else changes the picture

**The `kraken2_opt_v1.patch` documentation-staleness finding (boxed above) is itself the most consequential Q5 finding** — it's a concrete, present-tense instance of the exact docs-drift pattern this project's own memory index has flagged before, and it directly invalidated a specific recommendation four of seven independent agents converged on. Worth fixing `dorado-kraken-research/CLAUDE.md:151` directly, separate from any other outcome of this report.

**The hash-mix fix is a legitimate standalone contribution, independent of the pivot decision.** A correctly-hashed 4,096-set cache (3.58% hit rate) beats a broken-hash 262,144-set cache (1.42% hit rate) by 2.5× while using 1/64th the memory — a clean, well-instrumented, honestly-reproducible result ("hash quality dominates capacity for this workload's cache design") that stands on its own regardless of whether it ever shows up in end-to-end wall-clock.

**An external, independent cross-check on the entire cache-based premise, found by Agent G and worth citing directly:** the same `mtp1` branch's own separate lookaside-cache experiment concluded, on a real Kraken2 workload, *"no, in all three forms tested. The better it works, the slower it runs"* — a cache reaching up to 26.2% hit rate (far above anything Track A has measured) still lost to stock, because per-lookup probe cost outweighed the DRAM savings. This is a different failure mode than Track A's own (hit rate too low to matter, rather than hit rate high enough but probe cost too expensive) — worth citing in Track A's write-up as a second, independently-sourced data point on why a bounded lookup cache is a harder win than it looks, even when it works better than this project's own version does.

**A pre-registered go/no-go gate for the entire cache approach existed months before S1 was built and was never checked.** The May 2026 design doc that inspired the S1/S2 cache concept specified: "hit rate must be validated first... if `reuse_rate > 0.20`, patch is worth it." Measured hit rates across all of S1–S4's history top out at 3.58%, an order of magnitude under that threshold — though the `reuse_rate` metric that doc defines is not proven identical to the bounded-cache hit rate S1–S4 actually measured, so this is a real, source-grounded process lesson worth naming, not proof the whole approach was doomed from day one.

**Genuinely unresolved, not run by anyone in this exercise:** whether the reuse-distance shape (measured on `standard_8gb`, T=1 only) generalizes to `pluspf_103gb` or to realistic thread counts — `sample_targeted`/`pluspf_103gb` are already known to have different hit rates than `standard_8gb` from earlier minimizer-scheme differences, so this should be treated as `standard_8gb`-specific until spot-checked, not assumed universal.
