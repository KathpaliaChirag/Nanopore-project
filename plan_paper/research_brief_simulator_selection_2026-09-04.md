## The architecture question, resolved

Is the k-mer cache (S2) part of the hardware cache hierarchy, or separate from it? **Separate.** S2 is application-level code — a `thread_local` array kraken2 checks before calling the real hash table's `Get()` — not one of the CPU's L1/L2/L3 levels. But its own array is still ordinary memory, so it (and the hash table) both get cached by the real hardware hierarchy automatically, same as any other data the process touches. Both things are true at once: separate at the software/architecture level, not exempt from hardware caching.

This resolves the "approximate S2 as the LLC" awkwardness from the original draft of this brief, once you notice: **we don't need any simulator to invent associativity — 6 real S2 binaries already exist** (`s2_lru_{4,8,16,32,64}way_patch.py`, `s2_rr_patch.py` / `noatomics` variants, in `plan_paper/scripts/`). The right move for any of the three tools is to **run or trace the real, already-compiled S2 binary directly**, and let the simulator's modeled hardware hierarchy respond to whatever memory traffic that real code produces — not to reimplement S2 inside the simulator's own cache config. This sidesteps the "part of hierarchy or separate" question entirely: you're not asking the simulator to model S2 as a hardware level, you're letting real code (which already correctly sits in front of the hash table) run, and asking the simulator only for clean, confound-free timing underneath it.

### Q1 — Sniper vs. TEJAS: **Sniper, moderate-to-moderate-high confidence (~60-65%, not a clean win)**

Held across all 3 rounds, but confidence *dropped* from round 1's initial ~80% as verification surfaced real countervailing evidence:

- **Against a clean win**: (a) TEJAS's own validation is genuinely *tighter and more recent* than Sniper's — TEJAS reports 11.45%/18.77% mean error against a real, named 2012 Sandy Bridge machine (arXiv:1501.07420); Sniper's own published validation is ~25% error against 2006-2008 Core2/Nehalem hardware. Neither is within two microarchitecture generations of Luna's real Sapphire Rapids, but TEJAS's gap is smaller. (b) Sniper's own GitHub has several recent (Oct-Nov 2025), still-open issues of people following the official getting-started guide and hitting real failures — including a crash on the canonical `test/fft` smoke test itself, and a Pin-version mismatch (Sniper's manual only claims tested "up to Pin-3.7," current Pin defaults to 3.28-3.31+). "Self-serviceable, no outside dependency" should read as "self-serviceable, budget 1-2 days of build friction — this is common, not rare." (c) TEJAS has a real, if weaker, self-service path even without sir's help: a public Google Group with real traffic, not just "wait for an introduction."

### A critical, load-bearing finding that changes the whole plan: **simulation throughput, not tool choice, is the binding constraint**

Independently verified across all 5 agents and 2 rounds: Sniper has (at least) three execution modes with wildly different speed — **fast-forward** (~1000 MIPS, no timing model, used to skip DB-load/warmup) and **detailed/interval simulation** (~1 MIPS — the *only* mode that produces the cache-hit/timing stats this case study needs). Fast-forward only helps skip the parts nobody cares about; the classification hot path, where S2's actual behavior lives, must run in detailed mode. At ~1 MIPS against a real kraken2 run's ~10^10-10^12+ instructions, **a full-scale run is not feasible in 9 days, regardless of which tool wins** (TEJAS has no fast-forward equivalent at all — its trace-driven model pays full ~700x Pin-instrumentation cost for the entire captured region).

**This is now a hard requirement, not a nice-to-have**: the plan needs an explicitly small, deliberately truncated instruction window (e.g., a few million to low-hundreds-of-millions of instructions of real classification activity, small DB, 1-2 threads) — stated plainly in the paper as a proxy/microbenchmark, not "kraken2 under Sniper." `planning/week7plan.md` item 4's timeline previously budgeted zero explicit simulation wall-clock time; this is now fixed.

### Q2 — Hierarchical vs. single-level cache model: **single-level for the core 9-day deliverable, with a scoped 2-level (on-chip-fast / off-chip-slow) escalation path if time/ambiguity warrants — full 4-level hierarchy out of scope regardless**

This was the real fault line: Gamma argued a single collapsed level structurally cannot show whether S2's growing footprint (4→64 ways) spills from L2 into LLC/DRAM — the leading *mechanistic* candidate for the real-hardware "more ways, worse wall-clock" inversion — and that collapsing to one level answers a duller question. The other four (and eventually Gamma too, in a genuine round-3 concession) converged on: this is a real, legitimate cost, but (a) the project's own prior diagnosis (2026-09-02 debate, locked) already identified per-thread first-touch/allocation cost — not spillover — as the leading hypothesis for the real-hardware inversion, so a full hierarchy chases a secondary question with a scarce, already-oversubscribed budget; (b) a full hierarchy reintroduces exactly the kind of confound (coherence traffic, private per-core L1/L2 contention) this whole simulator pivot exists to eliminate, making it *harder*, not easier, to attribute a timing delta to S2's policy specifically; (c) it's strictly more expensive per instruction in the one mode that's already the bottleneck (detailed, ~1 MIPS), directly worsening the throughput problem.

**Final shape**: model S2 against a single modeled cache level standing in for "the backing store" for the primary result. If there's spare budget in the parallel track, a 2-level model (one fast on-chip level, one slow off-chip level, no separate coherence/LLC-sharing detail) is the cheapest version that could still show a capacity-threshold signal — run it only for the specific DB/thread cells where the real-hardware data showed the sharpest inversion (`sample_targeted`/T=1), not the full 6-variant sweep. Explicitly name the spillover question as **future work** in the paper's limitations section, not a silently dropped thread.

### Real native instruction throughput (MIPS) — Luna measured directly, Orion estimated

Not to be confused with the *simulator's* detailed-mode throughput (~1 MIPS for Sniper, ~140-175 KIPS for TEJAS) discussed above — that's the simulator modeling instructions, a completely different and far smaller number than real silicon.

**Luna — directly measured**, from an already-logged real `perf stat` run (`dorado-kraken-research/Luna/profiling/reads_fast_thread_scaling/standard_8gb_1T.txt`, single-threaded, no simulator involved): 101,230,972,490 instructions in 16.803871663s elapsed → **native IPS ≈ 6.03 billion/s (~6,026 MIPS / ~6 GIPS)**. Cross-checked via cycles (51,955,855,827 cycles / 16.804s ≈ 3.09 GHz effective clock × 1.95 IPC ≈ 6.03 GIPS) — the two routes agree exactly.

**Orion — estimated, not directly measured** (no raw instruction/cycle counts survived locally, only an aggregated IPC/time table in `AccuracyDrift/RESULTS.md`): measured IPC = 1.04 (`reads_sup`/`sample_targeted`/T=1) × NVIDIA's publicly documented max Cortex-A78AE clock on Orin, 2.2 GHz (MAXN power mode) → **estimated native IPS ≈ 2.29 billion/s (~2,288 MIPS / ~2.3 GIPS)**. Caveat: assumes the core ran at full 2.2 GHz throughout, unverified — Jetson boards often default to a lower power mode and can throttle under sustained load, so treat this as a plausible estimate (roughly a third of Luna's native speed), not a confirmed number the way Luna's is.

**Expected simulator wall-clock for one full single-threaded run**, using Luna's real 101.23B-instruction reference workload: Sniper fast-forward (~1000 MIPS) ≈ 101s but produces no timing data; **Sniper detailed mode (~1 MIPS) ≈ 28.1 hours**; **TEJAS (~140-175 KIPS) ≈ 178.6 hours (~7.4 days)**. Inverting: to keep one Sniper detailed-mode run under an hour, cap the window at ~3.6 billion instructions; for TEJAS, ~560-630 million.

**Open verification gap, not yet checked**: Sniper and TEJAS are both fundamentally Pin-based (x86 dynamic binary instrumentation). Neither tool's ARM64 support was confirmed in this research pass — if Orion's own ARM kraken2 binary needs to be simulated directly (not just cited for its real hardware numbers), verify Pin/Sniper/TEJAS ARM support before budgeting time for it; it may need a different tool entirely (e.g., DynamoRIO-based instrumentation).

### Real hardware cache replacement policy — mostly inferred from older chips, not confirmed for Luna/Orion's exact silicon

**Luna (Intel Xeon Platinum 8468, Sapphire Rapids/Golden Cove)**: not disclosed by Intel; reverse-engineered by independent research (["Reverse engineering of cache replacement policies in Intel microprocessors and their evaluation"](https://www.researchgate.net/publication/269302058_Reverse_engineering_of_cache_replacement_policies_in_Intel_microprocessors_and_their_evaluation), IEEE) identifies Intel's **L2** as an undocumented scheme called **"Quad-Age LRU"** (2 bits of age per line, 0-3; hit resets age to 0; miss evicts the leftmost age-3 line, inserts at age 1), and **L3/LLC** since Skylake-X as an **adaptive bimodal insertion policy** switching per-set-group between quad-age-style and a scan-resistant strategy depending on workload. **Confirmed only up through Skylake-generation chips** — no paper found re-verifying this for Golden Cove/Sapphire Rapids specifically. Treat as "architecturally very likely, not confirmed for this exact chip."

**Orion (ARM Cortex-A78AE, Jetson AGX Orin)**: **L1 (both I-cache and D-cache) is ARM-documented as PLRU** (pseudo-LRU) — this one is actually stated in ARM's own Cortex-A78 TRM, not just reverse-engineered. **L2**: ARM's TRM references a 24-bit "L2 victim RAM" structure backing the replacement decision, but the exact algorithm text could not be pulled from the TRM in this pass (same JS-rendering/fetch problem that blocked confirming the L2 associativity number earlier) — flag as unconfirmed, not assumed. **SLC (4MB, NVIDIA's own IP)**: no public information at all, consistent with NVIDIA staff explicitly declining to disclose cache internals on their own developer forum (same source as the associativity finding above).

**If pursued**: this is exactly the kind of gap CacheQuery-style empirical reverse-engineering (mentioned above) would close directly on the real hardware, rather than relying on inference from older/different chips in the same family.

### Multi-core scaling: aggregate throughput rises, per-core efficiency falls — verified on real Luna data, and the same shape applies to the simulator

Real, directly-measured comparison (`standard_8gb`, `reads_fast`, T=1 vs. T=32, same DB/read file/machine):

| | T=1 | T=32 |
|---|---|---|
| Total instructions | 101,230,972,490 | 103,649,763,060 |
| Elapsed wall time | 16.804s | 5.058s |
| **Aggregate IPS** | **6.03 billion/s** | **20.5 billion/s** |
| IPC | 1.95 | 1.69 |
| LLC-miss rate | 80.03% | 83.87% |

Aggregate throughput rose ~3.4x from 32x more cores — real, but sharply sublinear, because IPC dropped (1.95→1.69) and LLC-miss rate rose (80.03%→83.87%) as more threads contended for the same shared LLC/memory bandwidth. **No single core runs its own instructions faster because more cores exist** — turbo/frequency and shared-resource contention actually make each core individually less efficient as more of them are active simultaneously. This is the same mechanism behind this project's own already-documented finding that 32T is Luna's sweet spot and 96T is worse ("cache thrashing and contention outweigh parallelism," `dorado-kraken-research/CLAUDE.md`).

**The same shape applies to the simulator, and this is useful operationally**: Sniper's own published numbers show ~500 KIPS for one simulated core scaling to ~2 MIPS aggregate for 16 simulated (target) cores on an 8-core host — ~4x aggregate throughput from parallel host execution, sublinear for the same reason (shared modeled cache/interconnect state creates real dependencies). Two concrete implications for the plan: (1) **running the 6 independent S2 variants concurrently as separate host processes** is a guaranteed, near-linear win (Luna's 96 cores/192 threads make this trivial — 6, or many more, at once instead of sequentially) since they share no state; (2) simulating a multi-threaded target config (e.g., kraken2 at T=32) can benefit from host parallelism too, but with unverified scaling past the one documented 8-host/16-target data point — don't assume it scales linearly to Luna's 96 cores without checking. TEJAS's host-parallelism behavior for multi-core target simulation was not verified in this pass at all — check directly before assuming it behaves like Sniper here.
