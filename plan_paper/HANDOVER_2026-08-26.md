## Where things stand right now — READ THIS FIRST

An independent 5-agent/3-round audit (report: [`plan_paper/verification_report_2026-08-26.md`](https://github.com/KathpaliaChirag/Nanopore-project/blob/main/plan_paper/verification_report_2026-08-26.md)) found a **real architecture bug** in the S2 cache implementation, right at the end of this session, before it could be fixed. This is the most important thing to know:

### The bug: S2's cache is nested inside S1's gate, not standalone

S2 (the 4-way set-associative cache — sir's literal required baseline) was implemented by wrapping the `hash->Get()` call with `S2Lookup`/`S2Insert` **inside** the existing `if (*minimizer_ptr != s1_last_minimizer)` block (S1's adjacent-repeat check). This means: whenever a minimizer matches the one immediately before it, execution takes the `else { taxon = s1_last_taxon; }` branch and **S2 never even sees that lookup**. S2 only ever gets fed the "residual" stream of minimizers that already failed S1's filter — not the full lookup stream, as "sir's baseline" framing implies it should be.

**Why this matters:** every "S2 shows no measurable benefit" conclusion from this session's benchmarking is now suspect — it might be measuring "a standalone 4-way cache doesn't help" (a real, publishable negative result) or it might be measuring "a 4-way cache starved of most of its traffic by an upstream filter doesn't help" (an artifact of how we wired it, not a finding about 4-way caches). These are very different conclusions and the current data can't distinguish them.

**S2 is also still uncommitted on Luna** — a shared account (`student`) with an *already-documented* precedent for data loss (two ESKAPE databases vanished with an unresolved root cause). This is the single most urgent action regardless of anything else below.

### 2. Fix the nesting bug and re-measure S2 standalone

Move `S2Lookup`/`S2Insert` so they wrap the *entire* lookup decision, not just the piece inside S1's `if`. Concretely: S2 should be checked regardless of whether the minimizer matches `s1_last_minimizer` — either restructure so S2 sits in front of both S1's check and `Get()`, or (simpler, and worth considering) drop S1's separate adjacent-check entirely once S2 exists, since a 4-way cache checked first subsumes the 1-slot case as a special instance. Re-run the same validated 3-run interleaved methodology (`plan_paper/scripts/compare_s0_s1_s2.py`) against this fixed version before trusting any S2 "benefit" conclusion.

### 3. Add hit/miss instrumentation inside `S2Lookup`

Thread-local counters (hits, misses), printed at process exit. Cheapest, most direct way to know whether the cache is even firing at a sane rate — right now every "no benefit" conclusion rests entirely on external proxies (wall-clock, `perf stat` LLC-miss%), and the audit found this genuinely can't distinguish "cache legitimately rarely hits" from "cache never hits due to a bug in `S2SetIndex`/`S2Lookup`."

### 4. Run a real correctness check — diff actual classification output

Every benchmark so far used `--output /dev/null --report /dev/null`. Run `kraken2-fresh-bin-s0` and `kraken2-fresh-bin-s2` with **real** output files on a small DB (`sample_targeted`), `diff` them. This is nearly free (both binaries already exist) and directly resolves whether the S2 patch's correctness reasoning (decoupling cache hit/miss from `minimizer_hit_groups`/`curr_taxon_counts` stats-counting) actually holds, not just reads coherently.

### 5. Fix `week4plan.md`'s stale safe-zone ledger

It still shows all 4 S2 sub-steps as `⬜ not started` despite S2.1-S2.4 being done (audit item Q8.3) — actively misleading if anyone (including sir) trusts the ledger over the log.

### 6. Before finalizing S3's sizing formula: run the pre-touch experiment

Pre-touch/warm the `thread_local` arrays outside the timed region on the worst-case cell (`sample_targeted`, 96T, 4,194,304 sets), re-measure. If the cliff mostly disappears, first-touch cost is confirmed as dominant — this determines which mitigation S3 should actually implement (huge pages / avoid first-touch, vs. capping total footprint against LLC-fitting DBs). Also cheap to add: a `page-faults` counter to the existing `perf stat -e` list, no new binary needed.

**S3's pure design sub-steps (S3.1-S3.3 — topology detection, trace capture/synthesis, simulator work) don't touch the cache code and can start in parallel with all of the above**, per the audit's explicit go/no-go.

## Key operational knowledge (so you don't rediscover these the hard way)

- **Luna proxy/login:** the four `export HTTP_proxy=...` lines are baked into `~/.bashrc`, so `env -u ...` alone does NOT give a clean environment for `iitd-login.py` — use explicit `unset http_proxy https_proxy HTTP_proxy HTTPS_proxy` first, verify with `env | grep -i proxy` (must be empty), *then* run the login. The login session only stays alive ~100 seconds per cycle before the daemon auto-relogs — retry real operations in a loop rather than trying to time it manually (see `plan_paper/README.md` for the exact retry-loop pattern).
- **Benchmarking must interleave, never block.** Running "S0's full sweep, then S1's full sweep" produced a dramatic-but-fake result once (page-cache warmth from one binary's sweep benefiting from a prior sweep having already read the same 103GB file). Every comparison script now alternates binaries within each cell (S0,S1,S2,S0,S1,S2,...) specifically to prevent this. Don't simplify this back to sequential blocks.
- **Heredocs get mangled by this terminal** (lines dropped or duplicated on paste). For anything more than a few lines, base64-encode it into one unbroken line instead — see the exchange in this session's history around the size-sweep script for the exact pattern, or just ask for it again if needed.
- **`git tag` after a failed `git commit` still runs** if the two commands aren't `&&`-chained — this created a stale tag pointing at the wrong commit once (`safe/S1.2` briefly pointed at the pre-patch checkout). Always verify with `git log -1 <tag> --format='%H %s'` after tagging, don't trust a tag was created correctly just because the command didn't error.
- **This user wants commands explained in detail**: comment the code/command inline (why each meaningful line matters, what gain we're after, what we're building toward), then a short paragraph underneath tying it together — not just a one-line "why." Established explicitly mid-session.
