# S18 - fixed a CPU stall that S11 had introduced and never caught

built on: S17.

## original code: what it was doing

S11 (discarded, see `06_S11.md`) introduced a ring buffer for the scanner's
sliding-window queue, but its insert function still took a whole struct by
value and copied it in:

```cpp
inline void push_back(const MinimizerData &d) { buf[(head + n) & MASK] = d; n++; }
// called as:
MinimizerData data = { candidate_lmer, queue_pos_ };   // two 8-byte fields
                                                        // written to the stack...
queue_.push_back(data);                                // ...then read back as
                                                        // one 16-byte struct
```

## the issue

`perf annotate` on this exact function - something not done back in S11 -
found one instruction, a 16-byte load (`movdqa`) of the just-built struct,
eating **21% of the scanner's entire runtime** on its own (the scanner itself
was already 43% of all cycles). the two fields had just been written
separately, as two 8-byte stores, a moment earlier; the CPU cannot serve a
16-byte load from those two narrower, not-yet-committed stores (there's no
"store forwarding" path that covers this shape), so it has to stall and wait
for the stores to actually land before the load can proceed. this is exactly
why S11 measured no improvement: the new ring buffer still hit the same wall
the old `std::deque` always had, it just moved where the stall lived.

## new code: what changed

replace the two-field struct-copy with a push that writes both fields
directly into their final slot, so no intermediate 16-byte struct is ever
built or read back:

```cpp
inline void push(uint64_t candidate, ssize_t pos) {
  MinimizerData &d = buf[(head + n) & MASK];
  d.candidate = candidate;   // direct field store #1
  d.pos = pos;               // direct field store #2
  n++;
}
// called as:
queue_.push(candidate_lmer, queue_pos_);   // no stack temp at all
```

## why the result is still correct

the ring's contents and read-side behaviour (`front`/`back`/`pop_front`/
`pop_back`/`empty`/`clear`) are unchanged - only how a new entry gets written
in changed. same values end up in the same slots either way.

## result

another 2-3% on top of S17 (50MB -2%, 8GB -3%). confirmed with `perf
annotate`: the stalling instruction's share of the scanner's time dropped
from 21% to 3.9%.

## files touched

`mmscanner.h`, `mmscanner.cc`.
