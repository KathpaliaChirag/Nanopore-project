# S10 - parallel hash-table load

built on: S9 (file streaming + prefetch).

## original code: what it was doing

before any read is classified, kraken2 has to load the hash table
(`hash.k2d`, the database file) into memory. stock does this with one call,
on one thread, before the 32-thread pool is ever used:

```cpp
ifs.read((char *) table_, capacity_ * sizeof(*table_));
if (! ifs)
  errx(EX_OSERR, "Error reading in hash table");
file_backed_ = false;
```

## the issue

for the 103GB database, this single `.read()` took about 55 seconds out of a
roughly 90-second run - 60% of the total wall time was spent before a single
read was classified. two things happen serially inside it: the kernel copies
every byte from the page cache into the process's memory, and (first time
these pages are touched) the OS faults in every page as it's written. neither
is parallelized, because the thread pool that will later classify reads
doesn't exist yet at this point.

## new code: what changed

`compact_hash.cc`'s `LoadTable()`: split the table's bytes into 64MB chunks
and have up to 32 OpenMP threads each `pread()` their own chunk straight into
the table's memory, at the same time:

```cpp
int pfd = open(filename, O_RDONLY);
const size_t CHUNK = (size_t) 64 << 20;
size_t nchunks = (payload_bytes + CHUNK - 1) / CHUNK;
int nthr = std::min(omp_get_max_threads(), 32);

#pragma omp parallel for schedule(dynamic, 1) num_threads(nthr)
for (size_t c = 0; c < nchunks; c++) {
  size_t off = c * CHUNK;
  size_t len = std::min(CHUNK, payload_bytes - off);
  char *dst = ((char *) table_) + off;
  size_t done = 0;
  while (done < len) {
    ssize_t r = pread(pfd, dst + done, len - done, payload_off + off + done);
    if (r <= 0) { failed = true; break; }
    done += (size_t) r;
  }
}
```

`pread()` takes an explicit byte offset, so threads never share a file cursor
and never collide on where they're reading from. if the parallel path fails
for any reason (file won't open, a read comes back short), it falls straight
back to the original single-threaded `ifstream::read()`, so a problem here
never produces a broken table - it only loses the speedup for that run.

## why the result is still correct

the bytes landing in `table_` are byte-for-byte the same file, read in
different-sized, different-order pieces instead of one serial stream. the
table in memory is identical either way - this only changes how fast it
gets there.

## result (raw numbers, 3 interleaved reps, 1,872,777 reads, 32 threads)

| database | stock (S0) | S10 | speedup |
|---|---|---|---|
| 50MB | 16.45s | 11.61s | 1.42x |
| 8GB | 20.73s | 11.96s | 1.73x |
| 16GB | 25.42s | 13.80s | 1.84x |
| 103GB | 90.47s | 34.46s | 2.63x |

bigger table, bigger win - this is purely a load-time fix, so it scales with
database size, not read count. a separate spot check at only 10 reads on the
16GB database (where load time is nearly the whole run) showed the clearest
version of this: 9.14s to 1.89s.
