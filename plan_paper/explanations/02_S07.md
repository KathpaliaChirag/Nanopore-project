# S7 - S6 plus batched prefetch (null result)

## what it is

S6's cache, plus a batched software-prefetch scheme on top: instead of
looking up one minimizer at a time, scan a small batch (size set by the
`K2_B` environment variable, default 16), issue a hardware prefetch for each
one's table cell, then go back and resolve the whole batch. the idea is that
the memory fetch for item 2 starts while item 1 is still being resolved, so
the DRAM latency of several lookups overlaps instead of being paid one at a
time.

```cpp
while (n_pf < la_batch) {
  minimizer_ptr = scanner.NextMinimizer();
  pf[n_pf].hc = MurmurHash3(pf[n_pf].min);
  hash->Prefetch(pf[n_pf].hc);     // start the fetch, don't wait for it
  n_pf++;
}
for (int i = 0; i < n_pf; i++) {
  // ... resolve pf[i] here, in the same order as before
}
```

correctness is simple: pass 1 only hashes and prefetches, it never produces a
result. pass 2 resolves every slot in exactly the order the stock loop would
have, using the same logic. the sequence of taxa produced is identical.

## result

**no gain.** wall-clock came back at stock speed - the cache from S6 was
still doing nothing, and the prefetch on its own did not move the needle at
this point in the chain.

## why it didn't work (understood later)

two things were wrong at this stage, both fixed later: the batch was
resolved immediately after being filled, giving the prefetch almost no time
to land before being used (fixed properly in S16's pipelining); and the
scanner and lookup path still carried other costs (division, a slow
reverse-complement, a buffered-read bug) that dominated the profile, so even
a working prefetch couldn't show through yet. S9 re-tests the same prefetch
idea on a clean base and gets a real result on the 103GB database - the
batching itself was fine, this stage just wasn't isolating it correctly.
