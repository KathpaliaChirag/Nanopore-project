# S9 - batched prefetch, no cache

built on: stock + S8 (file streaming), with S7's prefetch idea re-applied -
but this time with the S6 cache left out entirely, on a cleaner base.

## original code: what it was doing

stock resolves one minimizer at a time:

```cpp
if (*minimizer_ptr != last_minimizer) {
  taxon = hash->Get(*minimizer_ptr);   // waits out the full memory latency here
  ...
}
```

`hash->Get()` for a large database is effectively a random read into a table
too big to fit in any cache - on the 103GB database this is a real DRAM
round-trip (~200 cycles) for almost every lookup, paid one at a time, serially.

## the issue

nothing overlaps: the CPU issues the memory request, then sits waiting for
it, then moves to the next minimizer and repeats. Luna's own earlier
profiling (outside this round) found DRAM bandwidth utilization at only
4.9-10.7% of peak during this kind of run - the bottleneck is latency, not
bandwidth, meaning there is real room to have several fetches in flight at
once instead of one.

## new code: what changed

the same two-pass batching S7 tried, re-applied on top of S8 instead of S6:

```cpp
int n_pf = 0;
while (n_pf < la_batch) {        // pass 1: scan + hash + prefetch a batch
  minimizer_ptr = scanner.NextMinimizer();
  pf[n_pf].hc = MurmurHash3(pf[n_pf].min);
  hash->Prefetch(pf[n_pf].hc);
  n_pf++;
}
for (int i = 0; i < n_pf; i++) {  // pass 2: resolve, same order as stock
  taxon = hash->GetWithHash(pf[i].min, pf[i].hc);
  ...
}
```

`la_batch` is read from the `K2_B` environment variable (default 16, 1 = the
exact stock one-at-a-time order) so the batch size can be swept without
rebuilding.

## why the result is still correct

pass 1 never produces a result, it only starts memory fetches. pass 2 runs
the identical per-minimizer logic stock has, in the identical order. the
taxa sequence is unchanged - confirmed byte-identical against stock.

## result (3 interleaved reps, 1,872,777 reads, 32 threads)

103GB: ~87s to ~76s - a real win, on the one database where lookups are
actually DRAM-bound. 8GB and 16GB: no measurable change - on those databases
the table largely fits in cache already, so there's little memory latency
left to hide.
