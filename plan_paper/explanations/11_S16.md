# S16 - pipelined prefetch

built on: S15.

## original code: what it was doing

S9's batching (still in place here) scans a batch, prefetches every item in
it, then immediately turns around and resolves that same batch:

```cpp
// fill batch, prefetch everything in it
// then, right away:
for (int i = 0; i < n_pf; i++) { /* resolve batch[i] */ }
```

## the issue

a prefetch takes time to actually land in cache. resolving the batch the
moment it's filled means the *first* items in the batch are read back almost
immediately after being requested - too soon for the memory system to have
delivered them. only the later items in a batch get much benefit from the
earlier prefetches.

## new code: what changed

keep two batch buffers and overlap them: while resolving batch N, start
scanning, hashing, and prefetching batch N+1 - so by the time N+1 is resolved,
its prefetches have had a whole batch's worth of resolve work to land during.

```cpp
PfSlot pfA[PF_MAX], pfB[PF_MAX];
PfSlot *cur = pfA, *nxt = pfB;
int n_cur = fill(cur);                 // batch 0, prefetched
while (n_cur > 0) {
  if (! exhausted) n_nxt = fill(nxt);  // start batch N+1's fetches EARLY
  for (int i = 0; i < n_cur; i++) {
    /* resolve batch N exactly as before, using its already-known idx */
  }
  std::swap(cur, nxt);                 // batch N+1 becomes the new "current"
  n_cur = n_nxt;
}
```

## why the result is still correct

the resolution logic inside the loop is byte-for-byte the same as every
earlier stage - same per-slot state (`min`, `hc`, `idx`, `amb`), same order,
same taxon/run-count bookkeeping. only *when* the next batch's prefetches are
issued changed, not what any lookup returns or what order results appear in.

## result (3 interleaved reps, 1,872,777 reads, 32 threads)

103GB: 19.18s to 17.21s (-10%). 16GB: -1.4%. 8GB: no measurable change - same
pattern as S9, this helps where lookups are actually memory-latency-bound.
