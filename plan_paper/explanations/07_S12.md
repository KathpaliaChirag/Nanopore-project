# S12 - remove the hidden divisions from the lookup path

built on: S10 (not S11 - that stage was discarded, so S12 was built from the
last stage that actually helped).

## original code: what it was doing

a 64-bit `%` (modulo) is one of the slowest basic arithmetic operations a CPU
can do - commonly 20-40 cycles, versus 1 for an add. the lookup path used it
twice per lookup:

```cpp
// in Prefetch():
__builtin_prefetch(&table_[hc % capacity_], 0, 3);   // division #1

// in GetWithHash(), moments later, same hc:
size_t idx = hc % capacity_;                          // division #2, same answer
...
idx += step;
idx %= capacity_;                                      // division #3, on every probe step
```

`perf` on S10's own profile showed `Prefetch` and `GetWithHash` together at
about 27% of cycles, much of it this repeated division.

## the issue

the same `hc % capacity_` was being computed twice for one lookup (once to
prefetch, once to actually read), and every step of the open-addressing probe
divided again even when it hadn't wrapped around the table.

## new code: what changed

**compute the index once.** `Prefetch` became `PrefetchIndex`, which computes
the index, issues the prefetch, and *returns* the index; `GetWithHash` became
`GetAt`, which takes that index instead of recomputing it:

```cpp
size_t CompactHashTable::PrefetchIndex(uint64_t hc) const {
  size_t idx = FastMod(hc);
  __builtin_prefetch(&table_[idx], 0, 3);
  return idx;
}
hvalue_t CompactHashTable::GetAt(hkey_t key, uint64_t hc, size_t idx) const {
  // ... same probe loop as before, starting from the already-known idx
}
```

**replace the division itself with a multiply.** `FastMod` uses a
precomputed reciprocal (`cap_recip_ = floor(2^64 / capacity_)`, computed once
when the table loads) and one 128-bit multiply plus a conditional subtract -
exact, same answer as `%`, no division instruction:

```cpp
inline uint64_t FastMod(uint64_t hc) const {
  uint64_t q = (uint64_t) (((unsigned __int128) hc * cap_recip_) >> 64);
  uint64_t r = hc - q * capacity_;
  return r >= capacity_ ? r - capacity_ : r;
}
```

**only divide on an actual wrap.** the probe loop's `idx %= capacity_` became
`if (idx >= capacity_) idx %= capacity_;` - skipping the division on the
(common) case where the probe step didn't carry past the end of the table.

## why the result is still correct

`FastMod` computes the exact same remainder as `%` for any divisor greater
than 1 (verified: `q` is `floor(hc/d)` or one less, so the correction never
needs more than one subtract). the table layout, hash values, and probe order
are completely unchanged - this only changes how `hc % capacity_` is
calculated, not what it equals.

## result (3 interleaved reps, 1,872,777 reads, 32 threads)

50MB: 11.62s to 10.98s. 8GB: no measurable change (this database's lookups
are memory-bound rather than CPU-bound, so shaving CPU cycles here has less
to show for itself).

## files touched

`kv_store.h`, `compact_hash.h`, `compact_hash.cc`, `classify.cc` (call sites
updated to the new `PrefetchIndex`/`GetAt` pair).
