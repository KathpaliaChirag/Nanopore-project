# S8 - stream all input files through one reader

built on: stock kraken2 (not on S6/S7 - the cache was dropped here).

## original code: what it was doing

the input for every benchmark in this project is 16 separate FASTQ files
(`pod5_0.fastq` ... `pod5_15.fastq`, 189MB to 1.04GB each, ~12.3GB and
1,872,777 reads combined - these come from a sequencer that writes multiple
pod5 files per run, not one). stock kraken2's main loop calls `ProcessFiles()`
once per file:

```cpp
for (size_t i = 0; i < opts.filenames.size(); i++) {
  ProcessFiles(opts.filenames[i], nullptr, hash_ptr, taxonomy, idx_opts,
               opts, stats, outputs, taxon_counters);
}
```

and `ProcessFiles()` opens one `#pragma omp parallel` region per call:

```cpp
BatchSequenceReader r1(filename1);
#pragma omp parallel
{
  // all 32 threads spawn here, process this one file, then this region ends
}
```

## the issue

a parallel region has a barrier at the end: every thread has to finish before
the region closes, so whichever thread runs out of work first for that file
sits idle waiting for the slowest one. with 16 files, this start/run/barrier
cycle happens 16 times instead of once. the file-handling cost itself is
small, but repeating the spin-up and wind-down of a 32-thread region 16 times
adds up.

## new code: what changed

two files. `classify.cc`'s loop now hands the first file *plus a list of the
rest* to a single `ProcessFiles()` call:

```cpp
} else if (! opts.paired_end_processing && opts.filenames.size() > 1 && i == 0) {
  std::vector<std::string> rest(opts.filenames.begin() + 1, opts.filenames.end());
  g_extra_files = &rest;
  ProcessFiles(opts.filenames[0], nullptr, ...);   // one call, all files
  g_extra_files = nullptr;
  break;
}
```

`seqreader.h`'s file reader learned to switch to the next queued file by
itself, in place, when it hits the end of the current one - without the
caller ever seeing a gap:

```cpp
bool AdvanceFile() {
  while (multi_ && multi_->next < multi_->files.size()) {
    int nfd = open(multi_->files[multi_->next++].c_str(), O_RDONLY);
    if (nfd < 0) continue;
    kseq_->f->f = nfd;       // swap the underlying file descriptor in place
    kseq_->f->is_eof = 0;
    return true;
  }
  return false;
}
```

and where the reader used to just `break` at end-of-file, it now checks
`AdvanceFile()` first and keeps going if there's another file queued - all
still inside the one parallel region that was already running.

paired-end input is untouched; this only applies when
`opts.paired_end_processing` is false.

## why the result is still correct

reads are still produced in exactly the same file order, same content, same
count - the only change is that 16 files look like one continuous stream to
the thread pool instead of 16 separate runs. byte-identical output was
confirmed against stock.

## result (raw numbers, 3 interleaved reps, 1,872,777 reads, 32 threads)

| database | stock (S0) | S8 | speedup |
|---|---|---|---|
| 50MB | 15.6s | 11.1s | 1.41x |
| 8GB | 19.7s | 14.6s | 1.35x |
| 16GB | 25.1s | 19.1s | 1.32x |
| 103GB | 89.9s | 85.3s | 1.05x |

the smaller the database, the bigger the win, because the per-file barrier
cost is a fixed overhead that matters more when the rest of the run is
short. on 103GB almost the entire run is spent loading the table (see
`05_S10.md`), so there's very little left for this fix to save.
