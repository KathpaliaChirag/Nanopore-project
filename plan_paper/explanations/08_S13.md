# S13 - memchr in the FASTQ parser

built on: S12.

## original code: what it was doing

kraken2 uses `kseq.h`, a small, widely-used FASTQ/FASTA parser. its line
scanner looks for the next newline one character at a time:

```cpp
for (i = ks->begin; i < ks->end; ++i)
  if (ks->buf[i] == '\n') break;
```

## the issue

this loop runs for every single line of every FASTQ record - header,
sequence, `+`, and quality string - across the whole input. a byte-at-a-time
scan is exactly the kind of loop a CPU's SIMD instructions are built to
replace. a standalone single-threaded timing test (parsing the full 12.5GB
input, no classification, just reading records) showed this loop was 65% of
all parsing time: **10.53 seconds just to scan for newlines.**

## new code: what changed

`memchr()` - the C standard library's "find this byte" function, which glibc
implements with vectorized (SIMD) code - replaces the manual loop:

```cpp
unsigned char *mp_ = (unsigned char*) memchr(ks->buf + ks->begin, '\n',
                                              (size_t)(ks->end - ks->begin));
i = mp_ ? (int)(mp_ - ks->buf) : ks->end;
```

this finds the exact same position the manual loop would have found; nothing
else in the surrounding function changed.

## why the result is still correct

`memchr` returns a pointer to the first occurrence of the byte in the given
range, or `NULL` if it isn't there - which is exactly what the loop was
computing, just faster. the records built from that position are identical.

## result

standalone parse-only test, full 12.5GB input, single thread: **10.53s to
3.88s** (2.7x). end-to-end with classification, 8GB database, 32 threads,
1,872,777 reads: 11.94s to 10.41s.

## files touched

`kseq.h`.
