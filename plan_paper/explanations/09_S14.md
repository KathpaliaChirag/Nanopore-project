# S14 - huge pages for the hash table

built on: S13.

## original code: what it was doing

the hash table is allocated with a plain `new[]`:

```cpp
table_ = new CompactHashCell[capacity_];
```

on Linux, memory is managed in 4KB pages by default; every page the table
touches needs its own entry in the CPU's translation lookaside buffer (TLB)
to map a virtual address to a physical one.

## the issue

for the 103GB database, this is an enormous number of 4KB pages - far more
than the TLB can hold entries for. on S13, the 103GB run showed `sys` (kernel)
time of 220 seconds out of 675 total CPU-seconds, almost entirely page faults
during the load (roughly 27 million of them). after loading, every
lookup into the table is a near-random access, so each one risks a TLB miss
and a multi-level page-table walk just to find out *where* the byte lives,
before it can even be read. checking Luna's kernel setting confirmed huge
pages were not in use at all (`AnonHugePages: 0 kB`, THP mode `madvise` -
meaning a program has to opt in, stock never does).

## new code: what changed

allocate the table 2MB-aligned with `posix_memalign` and tell the kernel to
back it with huge pages via `madvise(..., MADV_HUGEPAGE)`:

```cpp
size_t tbytes = capacity_ * sizeof(*table_);
void *hp = nullptr;
if (tbytes >= (2 << 20) && posix_memalign(&hp, 2 << 20, tbytes) == 0) {
  madvise(hp, tbytes, MADV_HUGEPAGE);
  table_ = (CompactHashCell *) hp;
  huge_alloc_ = true;
} else {
  table_ = new CompactHashCell[capacity_];   // unchanged fallback
}
```

one 2MB huge page replaces 512 ordinary 4KB pages, so the same amount of
memory needs far fewer TLB entries and far fewer page-fault events to set up.
the matching `free()` (instead of `delete[]`) is called only when
`huge_alloc_` is true, so the ordinary path is untouched.

## why the result is still correct

this changes nothing about what's stored or how it's addressed - it only
changes which physical pages back the same virtual memory, and at what
granularity. the table's contents and the code that reads them are identical
either way. if the kernel can't grant huge pages for some reason, it silently
falls back to normal 4KB pages and the program still works correctly - just
without this particular speedup.

## result (3 interleaved reps, 1,872,777 reads, 32 threads)

16GB: 11.9s to 9.15s. 8GB: 10.36s to 8.29s. 103GB: 35s to somewhere between
13s and 20s.

**the 103GB number has real variance**, unlike every other stage here: 4
back-to-back runs landed at 13.1-13.3s, but the same binary run right after a
non-huge-page binary (leaving memory more fragmented) landed at 20.2s. the
cause is that huge pages require 2MB of *physically contiguous* free memory,
which the kernel can't always supply on demand - stock's plain 4KB path has
no such dependency and shows no equivalent variance. treat the 103GB number
as a range, not a single figure, until this is characterized further.
