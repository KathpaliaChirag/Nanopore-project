# S19 - portability guard (no speed change)

built on: S18. this is the final build - every benchmark cited as "the
current best" elsewhere in this project is S19.

## original code: what it was doing

S14 added `madvise(hp, tbytes, MADV_HUGEPAGE)` to request huge-page backing
for the hash table. `MADV_HUGEPAGE` is a Linux-specific constant; on a system
whose headers don't define it (a different OS, or an older kernel's headers),
the code as written in S14 would simply fail to compile.

## the issue

none of this round's testing happened anywhere but Luna (Linux). shipping
S14's huge-page call unguarded would mean the whole binary refuses to build
on any machine where that one constant doesn't exist - an all-or-nothing
dependency on a feature that's genuinely optional.

## new code: what changed

one preprocessor guard:

```cpp
#ifdef MADV_HUGEPAGE
        madvise(hp, tbytes, MADV_HUGEPAGE);
#endif
```

if the constant isn't defined, the `madvise` call is simply skipped - the
2MB-aligned allocation from S14 still happens (that part is portable
`posix_memalign`), it just won't get the huge-page hint on that system.

## why the result is still correct

this doesn't change behavior on Linux at all (where the constant exists, the
code is identical to S14). on a system without it, the table is still
allocated correctly and classification still produces the same output - it
only loses the TLB benefit S14 was chasing, never correctness.

## result

no speed change - this stage exists purely so the binary builds cleanly
everywhere, not to go faster. combined with S17's `__int128` guard (see
`12_S17.md`), the two portability fixes in this round mean nothing in the
final chain hard-depends on a Linux- or x86-specific feature without a
fallback.

## the combined final number (S0 vs S19, every real fix stacked together)

32 threads, 1,872,777 reads, one run per cell, output byte-compared against
stock in every cell:

| database | stock (S0) | S19 | speedup |
|---|---|---|---|
| 50MB | 16.71s | 8.88s | 1.9x |
| 8GB | 21.17s | 9.18s | 2.3x |
| 16GB | 25.81s | 10.94s | 2.4x |
| 103GB | 95.62s | 20.08s | 4.8x |

at smaller read counts the gap is much larger (10-17x), because the fixed
per-run costs this chain removes (file-switching overhead, table load time)
dominate a short run far more than a long one. full 16-cell matrix (4
databases x 4 read counts) is in `plan_paper/s6_s15_speedup_report_2026-09-24.md`.

## not yet tested

only Luna (x86, Linux) has run any of this. Orion (ARM64 Jetson) was
unreachable this round - tcp/22 times out from both this machine and Luna,
and only the address/account are documented, no password is stored, so it
was set aside rather than guessed around. the code itself has no x86-specific
instructions (`__builtin_prefetch`, `posix_memalign`, `pread`, and the two
guards above are all portable), so a build should at least compile on ARM,
but that is genuinely untested, not assumed safe.
