# S6 - revived the 4-way cache (no atomics, fixed hash)

## where this starts

S1 through S5 are earlier work, from before this round, and this round does
not build on them. S1-S4 were all modifications to a 4-way per-thread cache
(`S2` in that earlier naming) sitting in front of the hash-table lookup. that
cache went through a crash fix (S3) and a bad-hash fix (S4), and both times
the wall-clock result was a flat null - the cache's own hit rate was too low
to matter either way.

this round starts over from the pristine, unmodified kraken2 v2.17.1 source
(`classify.cc.pre-s1.1.bak`, the backup taken before S1 was ever applied).
S6 is the first stage built on that clean base.

## what S6 is

the same cache idea as the old S2/S4, rebuilt on stock source: a 4,096-set,
4-way, round-robin, per-thread cache in front of `hash->Get()`, with the
hash-mixing fix already folded in, and the global atomic hit/miss counters
(which were separately proven to cause their own slowdown) removed.

```cpp
static const size_t S2_NUM_SETS = 4096;
static const size_t S2_WAYS = 4;
struct S2Entry { uint64_t tag = S2_EMPTY_TAG; taxid_t taxon = TAXID_MAX; };
static thread_local S2Entry s2_cache[S2_NUM_SETS][S2_WAYS];

static inline size_t S2SetIndex(uint64_t hc) { return hc & (S2_NUM_SETS - 1); }
static inline bool S2Lookup(uint64_t minimizer, uint64_t hc, taxid_t *out) {
  size_t s = S2SetIndex(hc);
  for (size_t w = 0; w < S2_WAYS; w++)
    if (s2_cache[s][w].tag == minimizer) { *out = s2_cache[s][w].taxon; return true; }
  return false;
}
```

before a real lookup, `S2Lookup` is tried first; on a miss, `hash->Get()` runs
and the result is written into the cache (`S2Insert`, round-robin eviction).

## result at the time

50MB: 15.6s to 13.4s. 8GB: 19.7s to 15.9s. this looked like a real win.

## what it turned out to be

building S8 (see `03_S08.md`) required an ablation: the same binary, minus
the cache entirely, to isolate what the cache itself was contributing.
result: **identical speed**, 11.06s and 14.48s either way, and `perf` showed
the same total CPU cycles for stock and S6 (174K vs 175K samples). S6's
speedup had nothing to do with the cache - it came from something else
entirely (the file-handling change that became S8), and the cache was simply
along for the ride in that binary.

**verdict: the cache adds nothing. it is dropped starting with S8 and never
brought back.** this is the third time a version of this cache has been
tested for a wall-clock effect (after the earlier S3 and S4 null results) and
the third time it has come back flat.

## files touched

`classify.cc` only - no separate patch script for this stage; S6 was built by
reusing an already-compiled binary from an earlier session
(`kraken2-fresh-bin-s2-rr-noatomics-hashmix-4way`), relabeled.
